# てなブクの開発

## 開発に必要なもの

- Apple シリコンの Mac と Xcode 27.1 以降（iOS 27.1 の SDK を含むもの。アプリが動くのは iOS 17 以降です）
- [XcodeGen](https://github.com/yonaskolb/XcodeGen)（`brew install xcodegen`）
- はてなの OAuth consumer key（ログインを使う機能を試すときだけ）

`Packages/TenabukuKit` は、Swift のツールチェーンがあれば Linux でもビルドとテストができます。

## 初回の準備

新しい Mac で開発を始めるときの手順です。上から順に進めます。シミュレーターで動かすだけなら、手順 1 から 5 までで足ります。手順 6 は、自分の iPhone で動かすときだけ行います。

コマンドは「ターミナル」アプリに貼り付けて実行します。ターミナルは、Finder の「アプリケーション」>「ユーティリティ」にあります。

### 1. Xcode を入れる

1. Mac App Store で Xcode を探して入れます。
2. Xcode を一度起動します。追加のコンポーネントを入れるか聞かれたら、iOS を選んで入れます。
3. ターミナルで次を実行し、コマンドラインの開発ツールが Xcode を使うようにします。Mac のログインパスワードを聞かれます。

   ```bash
   sudo xcode-select -s /Applications/Xcode.app/Contents/Developer
   ```

4. 次を実行し、`/Applications/Xcode.app/Contents/Developer` と表示されれば完了です。

   ```bash
   xcode-select -p
   ```

   `/Library/Developer/CommandLineTools` と表示されたら、上の `sudo xcode-select` のコマンドがまだ効いていません。このままだと、あとで `swift test` を実行したときに `XCTest` が見つからずに失敗します。

起動したときに iOS を入れ忘れたら、あとから次のコマンドで入れられます。Xcode の設定の Components からも入れられます。

```bash
xcodebuild -downloadPlatform iOS
```

### 2. Homebrew と XcodeGen を入れる

XcodeGen は、Xcode のプロジェクトを `project.yml` から作るツールです。Homebrew で入れます。

1. Homebrew が入っているかを確かめます。バージョンが表示されれば、次の 2 を飛ばして 3 に進みます。

   ```bash
   brew --version
   ```

2. 「command not found」と表示されたら、Homebrew を入れます。コマンドは [Homebrew の公式サイト](https://brew.sh/)に載っているものです。

   ```bash
   /bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/Homebrew/install/HEAD/install.sh)"
   ```

   終わると、最後に「Next steps」として、`brew` を使えるようにするためのコマンドが表示されます。表示されたとおりに実行し、ターミナルを開き直します。

3. XcodeGen を入れます。

   ```bash
   brew install xcodegen
   ```

4. 次を実行し、バージョンが表示されれば完了です。

   ```bash
   xcodegen --version
   ```

### 3. リポジトリを取得する

置きたい場所に移動してから、リポジトリを取得します。`git` は Xcode と一緒に入っています。

```bash
git clone https://github.com/y-saeki/vibe-applications.git
cd vibe-applications/tenabuku-app
```

ここから先のコマンドは、どれも `tenabuku-app` の中で実行します。

### 4. 自分用の設定ファイルを作る

見本をコピーして、自分用の設定ファイル `Config/Secrets.xcconfig` を作ります。このファイルは git の管理外です。

```bash
cp Config/Secrets.example.xcconfig Config/Secrets.xcconfig
```

ファイルには次の 3 種類の値を書きます。どれも、必要になるまでは空のままでかまいません。シミュレーターで動かすだけなら、何も書かずに次へ進めます。

- `HATENA_CONSUMER_KEY` と `HATENA_CONSUMER_SECRET`: はてなのログインを使う機能を試すときだけ要ります。取り方は下に書きます
- `DEVELOPMENT_TEAM`: 実機で動かすときだけ要ります。手順 6 で書きます
- `TENABUKU_BUNDLE_ID`: 既定のバンドル ID がチームで使えないときだけ書きます。手順 6 で書きます

はてなの consumer key と secret は、次の手順で取ります。

1. はてなにログインし、[OAuth 開発者向け設定ページ](https://www.hatena.ne.jp/oauth/develop)を開きます。
2. 利用上の注意に同意し、アプリケーションを登録します。名前、Web サイトの URL、ロゴの画像を求められます。審査はなく、登録した直後から使えます。
3. 登録したアプリケーションの設定で、scope の `read_public`、`write_public`、`read_private`、`write_private` を使えるようにします。
4. 同じページにある consumer key と consumer secret を、`Config/Secrets.xcconfig` の `HATENA_CONSUMER_KEY` と `HATENA_CONSUMER_SECRET` に書きます。

consumer key と secret はアプリの Info.plist に入ります。ビルドしたアプリを他人に渡すと、secret も一緒に渡ります。自分で使う前提の作りです。

### 5. シミュレーターで動かす

1. Xcode のプロジェクトを作って開きます。

   ```bash
   xcodegen generate
   open Tenabuku.xcodeproj
   ```

2. Xcode のツールバーの左側で、スキームが `Tenabuku` になっていることを確かめます。その右の実行先のメニューで、iPhone のシミュレーターを選びます。
3. 「Product」>「Run」を選ぶか、ツールバーの実行ボタンを押します。シミュレーターが開き、ホットエントリーの一覧が表示されれば完了です。

続けて、データ取得層のテストが通ることも確かめておきます。

```bash
cd Packages/TenabukuKit
swift test
cd ../..
```

pull のたびに `xcodegen generate` を実行するのが面倒なら、「ビルドと実行」の節にある git のフックを入れておきます。

### 6. 実機で動かす（必要なときだけ）

1. Xcode の「Xcode」>「Settings」>「Apple Accounts」で、Apple アカウントでサインインします。有料の Apple Developer Program に入っていない、個人の Apple アカウントでもかまいません。
2. iPhone を Mac につなぎます。実行先のメニューの「Manage Devices」から Device Hub を開き、iPhone を Mac とペアリングします。
3. iPhone の「設定」>「プライバシーとセキュリティ」で、「セキュリティ」の下にあるデベロッパモードをオンにします。再起動を求められるので再起動し、再起動のあとに出る確認で有効にして、パスコードを入れます。デベロッパモードの項目は、iPhone を Mac とペアリングするまで表示されません。
4. Xcode でプロジェクトのターゲット `Tenabuku` を選び、「Signing & Capabilities」でチームを選びます。
5. 選んだチームの ID を、ターミナルで確かめます。

   ```bash
   xcodebuild -showBuildSettings -project Tenabuku.xcodeproj -scheme Tenabuku | grep DEVELOPMENT_TEAM
   ```

   `DEVELOPMENT_TEAM = ` のあとに表示された英数字が、チームの ID です。

6. その ID を、`Config/Secrets.xcconfig` の `DEVELOPMENT_TEAM` に書きます。Xcode の画面で選んだチームは、`xcodegen generate` を実行すると消えるためです。設定ファイルに書いておけば、作り直しても残ります。
7. もう一度 `xcodegen generate` を実行します。実行先に iPhone を選んで、「Product」>「Run」を選びます。

「Signing & Capabilities」に、バンドル ID が使えないという警告が出ることがあります。そのときは、`Config/Secrets.xcconfig` の `TENABUKU_BUNDLE_ID` の行の先頭にある `//` を消します。そのうえで、自分だけが使う ID（`com.example.tenabuku` の `example` を自分の名前にしたものなど）を書き、`xcodegen generate` を実行し直します。

## ビルドと実行

`Tenabuku.xcodeproj` は `project.yml` から生成するもので、リポジトリには入れていません。pull したあとや `project.yml` を変えたあとは、生成し直します。

```bash
cd tenabuku-app
xcodegen generate
open Tenabuku.xcodeproj
```

Xcode でスキーム `Tenabuku` を選び、シミュレーターか実機で実行します。

ファイルを足したり消したりしても、`xcodegen generate` は要りません。`Tenabuku/` は同期フォルダ（Xcode 16 からの synchronized folders）なので、その下に置いたファイルは Xcode が自分で見つけてビルドに入れます。同期フォルダを使うために、プロジェクトの形式は `xcode16_0` にしています。`Info.plist` だけは、XcodeGen がリソースから外します。

pull やブランチの切り替えのたびに生成し直すのが面倒なら、git のフックを一度だけ入れておきます。

```bash
cd tenabuku-app
./scripts/install-git-hooks.sh
```

入れたあとは、pull（rebase を含む）とブランチの切り替えのあとに、`xcodegen generate` が自動で走ります。XcodeGen が見つからないときは生成せず、そのことを表示します。同じ名前のフックをすでに使っているときは、上書きせずに止まります。その場合は、そのフックに `xcodegen generate` の呼び出しを自分で足します。

## データ取得の層

データ取得層は、取得元がどれだけ変わりにくいかで 3 つのモジュールに分けています。3 つは互いに依存せず、共通の部品だけを `HatenaShared` から使います。はてな側が変わって読めなくなったときに、直す範囲を 1 つのモジュールに収めるためです。

| モジュール | 取得元 | 認証 | 変わりにくさ |
|---|---|---|---|
| HatenaOfficial | REST API（`bookmark.hatenaapis.com/rest/1/my/bookmark` ほか）、マイブックマーク全文検索（`/my/search/json`）、エントリー情報（`/entry/jsonlite/`） | REST API と全文検索は OAuth | 高い（公式ドキュメントあり） |
| HatenaFeed | ホットエントリー（`/hotentry/{category}.rss`）、キーワード検索（`/q/{keyword}?mode=rss`）、ユーザーのブックマーク（`/{user}/bookmark.rss`） | 不要 | 高い |
| HatenaUnofficial | 注目コメント（エントリーページ `/entry?url={url}` の HTML）、新着コメント（`/api/entry/{url}/bookmarks?commented_only=1`）、マイホットエントリー（`/api/my/feed_digest`）、非表示ユーザー（`/api/my/ignore_users`）、エントリーの画像（`/api/entry/info?url={url}`）、はてなスター（`s.hatena.ne.jp/entries.json`、`s.hatena.ne.jp/star.add.json`）、サイトのアイコン（`cdn-ak2.favicon.st-hatena.com`、`icons.duckduckgo.com`、`www.google.com/s2/favicons`） | コメント、スターの数、アイコン、エントリーの画像は不要。マイホットエントリー、非表示ユーザー、スターの付与は Web のログインの Cookie | 低い（非公開） |

2026 年 10 月 31 日に、ログインの要らないエンドポイントへ実際にリクエストを送り、形式を確かめました。ログインが要るもの（REST API、全文検索、OAuth のトークン発行）は、公式ドキュメントの記述に合わせて作ってあります。2026 年 11 月 4 日に、OAuth のトークン発行と、ブックマークの取得・保存・削除、タグの一覧を実際に試し、どれも読み取れることを確かめました。全文検索、ユーザー情報（`/rest/1/my`）、401 の応答はまだ見ていません。

タグの一覧（`/rest/1/my/tags`）は、ドキュメントではタグの配列を返すことになっています。`{"tags": [...]}` の形で返るという話もあります。実際の応答は読み取れましたが、どちらの形だったかは記録していないので、両方を受け付けたままにしています。

方針として、次のことを決めています。

- 書き込みは公式の OAuth API で行います。例外はスターの付与です。OAuth の API がないので、`HatenaUnofficial` に置いています。使えなくなったら、スターの付与だけを外せます。
- キーワード検索は `sort`、`date_begin`、`date_end`、`users` で期間と最低ブックマーク数を絞れます。過去のホットエントリーはこれで探す予定です。日付別のホットエントリーのページは HTML しかないので、使うなら `HatenaUnofficial` に置きます。
- 自分のブックマークの一覧と検索は、どちらも公式の全文検索 API を OAuth で使います。
- 新着コメントは、エントリーページが読み込むのと同じ `/api/entry/{url}/bookmarks?commented_only=1` から、100 件ずつ読みます。一覧の終わりが近づくと、応答の `cursor` で続きを読みます。公式のエントリー情報（`/entry/jsonlite/`）にも同じコメントがありますが、はてなの CDN で 3 時間キャッシュされるので、新しいコメントが数時間遅れて出ます（2026 年 11 月 6 日に確認）。こちらのキャッシュは 3 分です。端末の中のキャッシュは使わず、読み込み直すたびに取り直します。
- この API は、コメントの中の制御文字をエスケープせずに返すことがあります。JSON としては正しくないので、読む前に空白に置き換えます。
- 注目コメントは、エントリーページの HTML の注目コメントの欄（`js-bookmarks-popular`）から読みます。注目の並びを返す API がないためです。`/api/entry/{url}/bookmarks` は `sort=popular` を付けても新着順を返します（2026 年 11 月 5 日に確認）。ブックマークされていない URL は、エントリーページではなくサイトのページへ転送されるので、注目コメントは 0 件として扱います。エントリーページなのに注目コメントの欄がないときは、ページの形が変わったとみなして `parseFailed` にします。

## ログイン

ログインは OAuth 1.0a で行います。承認ページはアプリの中の `WKWebView` で開き、はてなが送るコールバックへの移動をそこで止めて、`oauth_verifier` を受け取ります。

`ASWebAuthenticationSession` を使わないのは、はてなが `tenabuku://` のような独自スキームのコールバックを受け付けないためです。2026 年 11 月 4 日に試すと、`/oauth/initiate` は `oauth_parameters_rejected=oauth_callback` を返しました。通るのは http(s) の URL と `oob` だけです。https のコールバックをアプリに戻すには、中継するサーバーかユニバーサルリンクが要ります。どちらも用意しないことにしました。

コールバックは `https://tenabuku.invalid/oauth-callback` です。`.invalid` は名前が引けないと決まっているドメインで、はてなはこの URL も受け付けます。アプリが移動の前に止めるので、端末の外へは出ません。はてなが `oauth_verifier` を付けずにここへ戻したときは、利用者が許可しなかったものとして扱います。

アクセストークンとはてな ID は、Keychain に 1 つの項目として保存します（サービス `io.github.y-saeki.tenabuku`、アカウント `hatena`）。端末のロックを一度解除したあとから読めるようにしてあり、他の端末には同期しません。ログアウトはこの項目を消すだけです。はてなにはトークンを無効にする API がないので、連携をやめるときは、はてなの設定で取り消します。

ログインが要る API が 401 を返したら、保存したトークンは使えないとみなします。それ以降はリクエストを送らず、ログインし直すよう表示します。ログインし直すと、保存したトークンを置き換えます。

## マイホットエントリー

マイホットエントリーを返す公式の API と RSS はありません。`/{はてなID}/hotentry` のページは Web でログインしていないと 403 を返します。そこで、アプリの中で Web にもログインし、その Cookie で読みます。

2026 年 11 月 5 日に、ログインしたブラウザで次のことを確かめました。

- `/{はてなID}/hotentry` の HTML には、記事の一覧が最初から入っています（`ul.js-user-bookmark-item-list` の中の `li.bookmark-item` が 20 件）。JavaScript で後から読み込むものではありません
- このページは前日の分を `/api/my/feed_digest?date=YYYYMMDD` から JSON で読み足します。`date` を付けなければ、その日の分が返ります。中身は HTML と同じ記事で、`item[].entry` に URL、タイトル、ブックマーク数（`count`）、本文の抜粋（`content`）、画像（`image_url`、null のこともあります）、日時（`created`）があります。並びは `item[].score` の高い順です
- ログインしていないと、どちらも 403 を返します。JSON の本文は `{"reason":"login required"}` です
- 古すぎる日付を求めると、`{"pager":{},"item":[]}` が返ります。日付の形が違うと 500 を返します

アプリは HTML ではなく JSON（`MyHotEntryAPI`）を読みます。中身は同じで、HTML より見た目の変更に強く、日時も取れるためです。URL にはてな ID も要りません。読むのはその日の分だけで、前の日はさかのぼりません。ホットエントリーの一覧と同じ見せ方にするためです。

記事が 0 件でも、仕様の変更とはみなしません。お気に入りと関心ワードをどちらも設定していない人や、その日まだ記事が選ばれていないときに、正しく 0 件になるためです。`item` がないなど、形が違うときだけ `parseFailed`（`unofficial.my-hotentry`）にします。

### Web のログイン

Web のログインは `WKWebView` で `https://www.hatena.ne.jp/login?location=https%3A%2F%2Fb.hatena.ne.jp%2F` を開いて行います。はてなブックマークのページ（`b.hatena.ne.jp`）を読み終えたら、ログインが済んだとみなして閉じます。移動を決める時点ではなく読み終えた時点にしているのは、はてなブックマークが最初のページで付ける Cookie も残すためです。

Cookie は、アプリのすべての `WKWebView` が使う既定の保存場所（`WKWebsiteDataStore.default()`）に、WebKit が保存します。アプリが自分で Keychain などに写すことはしません。そのため、OAuth の承認ページやアプリ内ブラウザではてなにログインしたときも、その Cookie が使えます。OAuth でログインした人は、Web のログインをしなくても読めることがあります。

読むときは、保存場所からすべての Cookie を取り出し、`b.hatena.ne.jp/api/my/feed_digest` に送られるもの（ドメイン、パス、期限で絞ります）だけを `Cookie` ヘッダーにして送ります。`URLSession` の Cookie の扱いは切っています。

どの Cookie がログインを表すのかは、`HttpOnly` のため確かめられていません。そこで、ログイン中かどうかは Cookie を見て決めず、最後に分かったことを `UserDefaults`（`webSessionSignedIn`）に覚えておきます。ログインの画面を閉じたときと、読み込めたときにログイン中とし、403 が返ったときと、設定でログアウトしたときにログインしていないとします。設定の「はてなの Web」の表示は、この値によります。

ログアウトでは、保存場所から `hatena.ne.jp` とそのサブドメインの Cookie を消します。アプリ内ブラウザで見ているはてなのページからもログアウトします。OAuth のトークンは消しません。

403 が返ったら、一覧の代わりにログインを促す表示を出します。赤い表示にはしません。ログインが済むと、一覧を読み直します。

## 非表示ユーザー

はてなで非表示ユーザーに指定した人のコメントは、注目と新着のどちらにも出しません。はてなのエントリーページと同じ見え方にするためです。

非表示ユーザーの一覧を返す公式の API はありません。はてなのサイトの `/api/my/ignore_users` を、マイホットエントリーと同じ Web のログインの Cookie で読みます（`IgnoredUsersAPI`）。2026 年 11 月 6 日に、ログインしたブラウザで次のことを確かめました。

- 応答は `{"users":["はてなID", ...],"cursor":"..."}` の形です。`limit` を付けないと 50 人ずつ返り、`cursor` で続きを読みます
- `limit=10000` を付けると、1,000 人を超える一覧が 1 回で返り、`cursor` は付きませんでした
- ログインしていないと 403 を返します。本文は `403 Forbidden login required` で、JSON ではありません

アプリは `limit=10000` で読み、`cursor` が付いていれば続きも読みます。`cursor` が前と同じときと、20 ページを読んだときは止めます。

コメントは、これまでどおりログインせずに読み、アプリの中で非表示ユーザーのものを除きます。注目コメントは、ログインしていないときのエントリーページから読むので、除いた分だけ件数が減ります。ログインしたブラウザで見るエントリーページとは並ぶ人数が違うことがあります。

一覧はコメントと同時に読みます。読んだ一覧は 10 分間使い回し、その間はもう一度読みません。コメントの画面を下に引っ張ったときは、10 分たっていなくても読み直します。端末には保存しません。

Web でログインしていないときは、何も除かずにコメントを出します。一覧を読めなかったときも、コメントは出します。そのときは、前に読めた一覧があればそれで除きます。読めなかった理由は統合ログに書きます。一覧が 403 を返したときは、マイホットエントリーと同じく、Web でログインしていないものとして扱います。

## スター

コメントの一覧で、コメントごとにはてなスターの数を出します。星を押すと、スターを 1 つ付けます（`HatenaStarAPI`）。

2026 年 11 月 7 日に、次のことを確かめました。

- はてなスターはコメントをそのブックマークのパーマリンク `https://b.hatena.ne.jp/{はてなID}/{yyyyMMdd}#bookmark-{eid}` で見分けます。日付はブックマークした日を日本時間で書いたものです。エントリーページの HTML では、各コメントの日時のリンク（`js-bookmark-anchor-path`）がこの URL です。記事の URL やエントリーページの URL を渡しても、スターは返りません
- `s.hatena.ne.jp/entries.json` は `uri` をいくつも受け付けます。返る `entries` には、スターの付いたものだけが入ります。ログインは要りません
- `stars` の要素はスターを付けた人（`name`、`quote`。まとめて付けたときは `count` も）か、数だけの数値です。スターが多いと、途中が 1 つの数値にまとめられます。たとえば `[{"name":"a"},67,{"name":"b"}]` は 69 個です。色付きのスターは `colored_stars` に色ごとに入ります
- 付与は、はてなスターのウィジェット（`s.hatena.ne.jp/js/widget/add_star.*.js`）が送るリクエストに合わせました。ログインの Cookie を付けて `entries.json` を読むと、`rks` が返ります。ログインしていないと `null` です。この `rks` を付けて `star.add.json?uri=...&rks=...` を読むと、スターが付きます。ウィジェットのスクリプトによると、ログインしていないと `{"is_guest":1}` が、受け付けられないと `{"errors":[...]}` が返ります

`star.add.json` の実際の応答はまだ見ていません。ウィジェットのスクリプトから読み取った形に合わせて作ってあります。

パーマリンクは注目コメントではエントリーページのリンクから取ります。新着コメントでは、応答の `location_id`（eid）と `created`（日本時間に直します）から組み立てます。新着の 100 件で試すと、組み立てた URL のうち 45 件が、スターの付いたコメントとして返りました。

数はコメントを出したあとで読みます。コメントの表示を待たせないためです。`entries` に入っていないコメントは 0 個とします。数は色ごとに分けて、色付きのスター（`green`、`red`、`blue`、`purple`）を、はてなの返した順に黄色のスターの前に並べます。知らない色は灰色で出します。星を押して付けるのは、黄色のスターだけです。`uri` は 20 個ずつに分けて、同時に求めます。URL を長くしすぎないためです。読むときは Cookie を送りません。数を読めなかったときは、数を出さずにコメントだけを出し、理由を統合ログに書きます。

スターは、星と太字の数を、そのスターの色を薄く敷いたカプセルに入れて出します。色は、はてなのカラースターショップ（https://www.hatena.ne.jp/shop/star）にあるはてなスターのロゴと同じ色です。シートは後ろのページが透けるので、カプセルを敷いて、どのページの上でも数が読めるようにしています。数の色は、カプセルの上で読めるように、同じ色をライトモードでは暗く、ダークモードでは明るくします。星には、数と同じ色で薄い縁取りを付けます。日時とスターは 10pt で出し、文字サイズの設定に合わせて大きさを変えます。0 個のときと数を読む前は、灰色のカプセルに灰色の星を出します。スターを付けると、カプセルと星と数が黄色に変わります。

付与では、Web のログインの Cookie のうち `s.hatena.ne.jp` に送られるものを送ります。Cookie がないときと、`rks` や `is_guest` がログインしていないことを示したときは、ログインの画面を開きます。ログインが済むと、そのスターを続けて付けます。はてなが受け付けなかったときは、`errors` の中身を出します。数はスターが付いたという応答を受けてから 1 つ増やします。

スターを外す機能はありません。付けたスターは、はてなのサイトで外します。

マイブックマークの一覧でも、自分のコメントの下にスターの数を出します。ここでは数を出すだけで、付与はしません。パーマリンクは全文検索の応答の `eid` と `timestamp`（日本時間に直します）と、ログインしているはてな ID から組み立てます。全文検索 API のドキュメントには `eid` が載っており、2026 年 11 月 10 日に、組み立てた URL でスターの数が返ることを確かめました。非公開のブックマークにはスターが付かないので、求めません。

数は一覧の 40 行ずつの区切りで、行が画面に入ったときに読みます。行ごとに読むと、1 行スクロールするたびに問い合わせることになるためです。区切りの後ろ半分の行が画面に入ったら、次の区切りも読み始めます。一度読んだものは一覧を下に引っ張るまで読み直しません。引っ張ったときは、先頭の区切りを読み直し、残りは画面に入ったときに読み直します。読めなかったものは次に画面に入ったときに読み直します。

## サイトのアイコン

ホットエントリーとマイブックマークの一覧で、タイトルの上の行に、ドメインとサイトのアイコン（favicon）を出します（`FaviconClient`）。アイコンの大きさは 13pt で、ドメインの文字とほぼ同じ高さです。

アイコンを読む先は 3 つあり、設定の「サイトのアイコン」で、使うかどうかと問い合わせる順番を選べます（`FaviconPreferences`）。上から順に問い合わせ、最初に見つかったアイコンを使います。設定は UserDefaults に保存し、変えたときは、それまでに読んだアイコンを捨てて読み直します。

| 取得先 | 問い合わせる URL | 送るもの | 最初の設定 |
|---|---|---|---|
| はてな | `cdn-ak2.favicon.st-hatena.com/64?url={記事の URL}` | 記事の URL | 1 番目、オン |
| DuckDuckGo | `icons.duckduckgo.com/ip3/{ドメイン}.ico` | ドメインだけ | 2 番目、オフ |
| Google | `www.google.com/s2/favicons?domain_url={記事の URL}&sz=64` | 記事の URL | 3 番目、オン |

どれも公開された仕様はありません。2026 年 11 月 7 日に、次のことを確かめました。

- はてなブックマークの Web はホットエントリーのページで、はてなの URL を使っています。はてなは記事のページが宣言しているアイコンを探しますが、SVG のアイコンは変換できません
- DuckDuckGo はドメイン単位で答えます。ページが宣言している自分用のアイコンではなく、サイト全体のアイコンが返ります
- Google は `domain_url` に記事の URL を渡すと、そのページが宣言しているアイコンを返します。SVG のアイコンも PNG に変換して返します（`musica-terra.com/interactive/modal-earth/` で確かめました）。`domain` にドメインを渡すと、サイト全体のアイコンが返ります

最初の設定を「はてな → Google」にしているのは、はてな以外に記事の URL が伝わる場面を、はてなが答えられなかった記事に限るためです。DuckDuckGo はドメインしか送らない代わりに、ページごとのアイコンが出ないので、オフにしてあります。記事のサイトから直接読むことはしません。一覧を出すだけで、まだ開いていない記事のサイトに問い合わせることになるためです。

はてながアイコンを返さないのは、次の 2 つの場合です。どちらも、はてなは同じ 16×16 の灰色の画像を返します。アプリはこの画像のバイト列を持っていて、届いた画像と同じなら、アイコンがなかったものとして扱います。

- サイトにアイコンが見つからないとき。404 で返ります
- アイコンは見つかったが、はてなが変換できなかったとき。SVG のアイコンがそうで、200 で返ります

DuckDuckGo と Google は、アイコンがないときは 404 とともに代わりの画像を返します。404 なら使いません。DuckDuckGo の ICO には大きさの違う画像がいくつか入っているので、いちばん大きいものを使います。

どこにもアイコンがないとき、どこにもつながらないとき、すべてオフのときは、背景のない灰色の地球の記号を出します。読み込んでいる間は何も出しません。読めなくても赤い表示は出しません。読んだアイコンはアプリを閉じるまで記事の URL ごとに覚えておき、同じ記事では問い合わせ直しません。

## ホームの棚

ホームでは、カテゴリーごとのホットエントリーを「棚」にして縦に並べます（`HomeView.swift`）。App Store の一覧と同じ形です。棚の中は 3 件で 1 ページにし、ページを横に並べます。ページの幅は画面より少し狭くし、次のページの端が見えるようにしています。横にスクロールできることを、それで伝えるためです。スクロールはページの端で止めます。

画面に並べるページの数は、横のサイズクラスで決めます。コンパクトのとき（iPhone と、Duo の外側のディスプレイ）は 1 ページ、レギュラーのとき（Duo の内側のディスプレイ）は 2 ページです。広い画面で 1 ページを横いっぱいに伸ばすと、行が長くなって読みにくいためです。Duo を半分に折ったときに折り目がページの間に来るよう、2 ページにしています。グリッドの列を偶数にすることを、Apple の HIG が勧めているためです。どちらの場合も、並べたページで画面の幅の 88% を使い、残りに次のページの端を出します。

棚の行は、タイトルが短くても 3 行分の高さを取ります。隣り合うページで行の高さがそろわないと、横にめくるたびに棚の高さが変わるためです。

棚の見出しをタップしても、何も開きません。カテゴリーの全件を 1 本のリストで見る画面は、使ってみて要ると分かったら足します。

棚は画面に入ったときに読み込みます（`ShelfFeedStore`）。起動しただけでは 11 のカテゴリーをすべて読まないようにするためです。読んだ棚はアプリを終えるまで覚えておき、スクロールして戻ったときはすぐに出します。画面を下に引くと、それまでに読んだ棚をすべて同時に読み直します。読み直しのあいだは前の記事を出したままにし、失敗したときもそのまま残して、棚の上にエラーを出します。

ミュートした記事は棚に出しません。

どの棚をどの順番で出すかは `HomeShelves` モジュールの `ShelfPreferences` で持ち、UserDefaults に保存します。最初は、はてなのカテゴリーの順にすべて出し、マイホットエントリーを最後に置きます。保存にはカテゴリーの名前としてフィードの URL にある名前（`it` など）を使います。あとのバージョンで棚が増えたときは、出す状態で末尾に足します。知らない名前の棚は読み飛ばします。

棚の設定は設定画面の「表示する棚」から開きます（`ShelfEditorView`）。並べ替えのために、List を編集モードにしたままにしています。出す棚の印は行ごとのボタンで切り替え、ボタンは borderless にして編集モードでもタップを受けるようにしました。List の選択の印を使わないのは、選択した行を 1 行ドラッグすると、選択したすべての行がいっしょに動いてしまうためです。

## 一覧の画像を先に読む

ホットエントリーとマイブックマークの一覧では、画面に入る前の行のアイコンと記事の画像（`og:image`）を先に読みます（`ImagePrefetch`）。スクロールしたときに、画像が 1 つずつ遅れて出るのを避けるためです。

行が画面に入るたびに、その下の 15 行の分を読み始めます。ホームの棚では、ページが画面に入るたびに、その棚の後ろの 15 件の分を読み始めます。一覧の全部を一度には読みません。マイブックマークの一覧は数千件になることがあり、まだ見ない行まで読むと、通信とメモリを無駄に使うためです。読み終わった画像と読んでいる途中の画像は、同じ URL では問い合わせ直しません。

記事の画像は、メインスレッドの外で一覧に出す大きさ（標準の文字の大きさの行に合う 96pt を 3 倍した 288 ピクセル）に縮め、行が見せる中央の正方形だけを切り出してから覚えます（`ThumbnailCache`）。大きな画像をそのままの大きさで持たないためです。横長の画像も切り出すと 1 枚あたり約 324KB になり、正方形の画像と同じ大きさです。ホームの 10 前後の棚がそれぞれ 15 件先まで読んでも上の棚の画像が押し出されないよう、覚えておく量は 96MB（約 300 枚）までにしています。超えたときやメモリが足りなくなったときは、システムがその一部を捨てます。つながらなかった画像は覚えず、行がもう一度画面に入ったときに読み直します。

先に読んだ画像は、行が画面に入った最初のフレームから出ます。

マイブックマークの全文検索の応答には記事の画像がありません。そこで、エントリーページが読み込む JSON（`/api/entry/info?url={url}`）の `image` から、記事の画像の URL を求めます（`EntryImageAPI`、`EntryImageLookup`）。ホットエントリーの RSS の `hatena:imageurl` と同じ、はてなが用意した画像です。公式のエントリー情報（`/entry/jsonlite/`）の `screenshot` は、どのページでも「画像なし」の画像を返すので使えません（2026 年 11 月 10 日に確認）。はてなが知らない URL には 404 が返るので、画像なしとします。

はてなが画像を持たない記事もあります。2026 年 11 月 11 日に確かめたところ、`og:image` が WebP や AVIF のページと、画像の URL に日本語を含むページでは、RSS の `hatena:imageurl` も `/api/entry/info` の `image` も空でした。アプリはこれらの画像も表示できるので、はてなに画像がないときは、記事のページの HTML を読んで、`<head>` の `og:image`（なければ `twitter:image`）を使います（`PageImageAPI`、`PageImage` モジュール）。ホットエントリーで `hatena:imageurl` が空の記事は、はてなに問い合わせ直さず、すぐにページを読みます。ページは、はてなではなく記事のサイトから読みます。そのため、読めなくても、はてなの形の変化を示す赤い表示の記録（`FailureLog`）には残しません。

ページは先頭から `</head>` までだけを受け取り、そこで通信を打ち切ります。`</head>` が来ないときも、64KB で打ち切ります。2026 年 11 月 11 日に調べた 5 ページは全体が 59〜135KB で、`og:image` は先頭の 5KB 以内に、`</head>` は 30KB 以内にありました。

この URL は画像と同じく、画面に入る前の 15 行の分を先に求め、わかったら画像も読み始めます。求めた結果はアプリを閉じるまで覚え、つながらなかったものは覚えません。求めている間は、画像の枠を空のまま出します。

## 長押しのプレビュー

ホットエントリーとマイブックマークの一覧で行を長押しすると、記事のページをプレビューで出し、その下にメニューを出します（`PagePreview.swift`）。SwiftUI の `contextMenu(menuItems:preview:)` では、プレビューをタップしたときの動作を決められないため、UIKit の `UIContextMenuInteraction` を使っています。プレビューをタップすると、記事のブラウザが同じ Web ビューを引き継ぐので、ページを読み直しません。

ページは、プレビューが開く前から読み始めます。指が行に触れたまま 0.12 秒動かなければ、その行の記事を読み始めます（`PagePreloader`）。長押しと判定されるまでの約 0.5 秒のうち、0.4 秒ほど早く読み始められます。指が 8pt より大きく動いたときはスクロールとみなして読み込みを止め、そのまま普通のタップで記事を開いたときは、読み始めていたページを引き継ぎます。

先に読むページは 1 つだけです。Web ビューは 1 つごとに Web のプロセスとメモリを使うためです。読み込みに失敗したページは引き継がず、ブラウザが読み直してエラーを表示します。

ページがまだ描かれていないあいだは、プレビューにサイトのアイコン、サイト名、タイトルを出し、その下に本文の形をした灰色の線をゆっくり点滅させ、読み込みの進み具合はプレビューの上端のバーで示します。読み込みが半分まで進むか終わると、ページに切り替えます。

長押しで持ち上げる行の絵は、一覧ではその行のセルです。ホームの棚にはセルがないので、行のある範囲の画面を写したものを持ち上げます。写すのは持ち上げるときの 1 回だけで、閉じるときも同じ絵に戻します。閉じるときに写し直すと、その範囲を覆っているプレビューのページが写り、行がしばらくページの絵のまま見えるためです。

iOS 27 では、メニューに「Siri に頼む」の項目が自動で加わります。アプリからこの項目を外す公開の API はありません。

## ブックマークの編集

ブックマークの画面を開くと、その記事の自分のブックマークとタグの一覧を同時に読みます。タグの一覧が読めなくても、編集はできます。

タグの候補は、入力した文字を含むものを、入力の先頭と一致するもの、それ以外の順に並べます。それぞれの中では、使った回数の多いものが先です。大文字と小文字、全角と半角は区別しません。入力が空のときは、使った回数の多い順に 20 個だけ並べます。すべて並べると、タグを長く使っている人では候補が数百行になり、その下にある削除のボタンまで届かなくなるためです。保存するとき入力欄に文字が残っていれば、それもタグとして足します。

## 自分のブックマークの一覧

自分のブックマークを、非公開のものも含めて一覧できる公式の API はありません。REST API は 1 件ずつの取得・保存・削除だけで、ユーザーのブックマークの RSS には公開のブックマークしか出ません。そこで一覧も全文検索 API で作ります。

全文検索 API のドキュメントに書かれていないことを、2026 年 11 月にログインしたブラウザで確かめました。次のとおりです。

- 検索語が空だと、`total` が 0 で何も返りません。`*` も同じです
- 結果は、ブックマークした日時の新しい順に返ります。並べ替えの `sort` は 2018 年に廃止されていますが、これは指定しなくてもそうなります
- `https` で検索すると、ほぼすべてのブックマークに当たります。URL も検索の対象だからです。ただし、URL が `http://` で始まるものは漏れます
- `OR` は使えません。`http OR https` は、なぜか 97 件にしか当たりませんでした
- 1 つの検索で読めるのは 10,000 件目までです（`BookmarkAPI.searchDepth`）。そこから先を求めると、`total` が 0 で何も返りません。アプリは、10,000 件目を越えるページを求めません

そこで一覧（`MyBookmarkTimeline`）は、`https` と `http` の 2 つの検索を並べて読みます。読んだものは、ブックマークした日時の新しい順に 1 本にまとめます。両方に当たったブックマークは 1 回だけ並べます。

片方の手元の分がなくなったら、次のページが来るまで、もう片方も並べません。まだ読んでいないページに、より新しいものがあるかもしれないためです。片方の検索が最後まで尽きたときは、もう片方だけで続けます。片方が 10,000 件目に届いたときは、そこで一覧を終えます。その先と、もう片方の残りとの順番が分からなくなるためです。一覧の末尾には、それより前は検索すると見つかる、と出します。ブックマークが 3 万件ほどの人で、2022 年 10 月ごろまでさかのぼれます。

検索語を入れたときは、その検索 1 つ（`MyBookmarkPages`）を返った順に並べます。ここでも 10,000 件目までしか読めません。

索引は非同期で作られるので、ブックマークしたばかりの記事はしばらく出ません。

全文検索 API は遅いので、一覧（`MyBookmarkTimeline`）は端末に保存します（`MyBookmarkTimelineStore`）。2 回目からは、保存した一覧をすぐに出し、はてなには問い合わせません。公式アプリと同じやり方です。一覧を下に引っ張ると、新しいほうから読み直します。読み直しが済むまでは、それまでの一覧を出したままにし、失敗したときもそのまま残します。

保存するのは、2 つの検索をどこまで読んだかも含めた一覧の状態です。そのため、保存した一覧を下までスクロールすると、続きを読みます。保存してから後にブックマークが増えたり減ったりしていると、続きの区切りがずれます。増えた分は同じ URL を 2 回並べないことで吸収できますが、減った分だけ読み飛ばすものが出ます。引っ張って読み直せば直ります。

保存先は Caches の `MyBookmarks.json` です。システムに消されても、はてなから読み直すだけで済むためです。非公開のブックマークを含むので、端末のロック中は読めないように保存し、ログアウトしたときに消します。持つのは 1 つのアカウントの一覧だけで、別のアカウントでログインしたときは使いません。検索の結果は保存しません。

全文検索 API は、何件求めても 1 回に 3 秒ほどかかります。そのため一覧の 2 つの検索は、同時に読みます。一覧も検索も、1 回の読み込みで 50 件以上増えるまでページを読みます。末尾から 25 行目が見えたら、続きを読み始めます。読み込みの途中でブックマークが増えると、件数の区切りがずれ、同じブックマークがもう一度返ることがあります。同じ URL は 2 回並べません。空のページが返ったら、`total` が残っていても続きを読みません。

一覧から開いたブックマークの画面で保存や削除をすると、その行だけを手元で書き換えます。全文検索の索引がすぐには追いつかないためです。

保存する一覧には形式の番号を付けます。番号が今のアプリと違う一覧は使わず、はてなから読み直します。番号 2 から、各ブックマークの `eid` を保存しています。それより前に保存した一覧には `eid` がなく、スターの数を求められないためです。

全文検索の応答の `comment` は、タグを `[タグ]` の形で先頭に付けたものです（2026 年 11 月 10 日に確認）。一覧では先頭の `[タグ]` を本文から分け、コメントの画面と同じく本文の後ろに出します。閉じていない `[` と、中身のない `[]` からあとは本文とします。REST API で保存したブックマークはコメントとタグが分かれて返るので、手元の行を書き換えるときは、同じ形に組み立て直します。

一覧の画面はホットエントリーの一覧のツールバーから開きます。行をタップしたときは、ホットエントリーと同じ `FeedItem` を渡してアプリ内ブラウザを開くので、既読の記録も同じように付きます。

## 既読の記録

開いた記事は、ホットエントリーの一覧とホームの棚でタイトルを薄く表示します。マイブックマークの一覧では薄くしません。どれも自分でブックマークした記事なので、薄くしても見分けがつかないためです。記録するのは、一覧からアプリ内ブラウザを開いたときです。キーは一覧のエントリーの URL です。記事の中でリンクをたどっても、開いた元のエントリーが既読になります。

記録は `ReadingHistory` モジュールにあり、ネットワークには触りません。エントリーの URL ごとに、最後に開いた日時を持ちます。アプリは Application Support の `ReadHistory.json` に保存します。変わるたびに書き出し、起動のときに 30 日より古い記録を消します。もう一度開くと、その記事の 30 日は開いた日から数え直します。

30 日にしたのは、次の理由です。

- ホットエントリーは数日で一覧から消えるので、それより長く持っても使い道がありません
- 将来ほかの RSS を読めるようにしたとき、更新の遅いフィードでもひと月あれば足ります

ファイルが壊れていて読めないときは、記録を空にして始めます。理由は統合ログ（カテゴリー `read-history`）に書きます。設定画面の「既読の記録を消す」で、すべての記録を消せます。

## ミュート

ミュートの条件に合うエントリーは、一覧に出しません。条件は `EntryMute` モジュールにあり、ネットワークには触りません。アプリは Application Support の `MuteRules.json` に保存し、変わるたびに書き出します。

条件ごとに、対象（URL かタイトル）と書き方（ワイルドカードか正規表現）を選びます。読み方は次のとおりです。

| 対象 | 書き方 | 一致するもの |
|---|---|---|
| URL | ワイルドカード（`/` なし） | ホスト名。そのサブドメインも含みます。`example.com` は `www.example.com` にも一致し、`notexample.com` には一致しません |
| URL | ワイルドカード（`/` あり） | スキームを除いた URL の先頭。`example.com/blog/` は、その下のすべての記事に一致します |
| URL | 正規表現 | スキームを含む URL 全体のどこか |
| タイトル | ワイルドカード | タイトルのどこか |
| タイトル | 正規表現 | タイトルのどこか |

ワイルドカードでは、`*` が任意の文字列、`?` が任意の 1 文字です。大文字と小文字、全角と半角を区別しません。入力の頭に `https://` などが付いていれば外して読むので、URL をそのまま貼っても使えます。正規表現は Swift の `Regex` で読み、大文字と小文字だけを区別しません。

条件の数に上限は設けていません。その代わり、条件は変わったときに一度だけ組み立て直し、一覧を描くたびには組み立てません。正規表現が読めない条件は保存できません。保存したあとで読めなくなった条件があれば、その条件だけを無視します。

ファイルが壊れていて読めないときは、`MuteRules.unreadable.json` に名前を変えてよけ、空の状態で始めます。既読の記録と違って利用者が自分で作ったものなので、次の保存で上書きしないようにしています。理由は統合ログ（カテゴリー `mute`）に書きます。

## 壊れたときの検知

はてなの応答が想定した形でないとき、各クライアントは `HatenaError.parseFailed(source:detail:)` を投げます。`source` は取得元の名前（`feed.hotentry`、`unofficial.entry-page-popular` など）です。ホットエントリーが 0 件の場合も、フィードの形が変わったとみなしてこのエラーにします。

アプリはこのエラーを赤いバナーで表示し、統合ログにも書きます。Mac のコンソール.app でサブシステム `io.github.y-saeki.tenabuku` を指定すると、詳細を読めます。通信の失敗や HTTP のエラーは別の表示にしています。

## アイコン

アイコンは Icon Composer のデータ `Tenabuku/AppIcon.icon` です。iOS 26 以降の Liquid Glass の表現は、OS がこれから描きます。背景の色と、前景の 2 つの層（白い「て」と、オレンジのしおり）を分けて持っています。光沢や透け感は OS が付けるので、絵には描き込んでいません。

ダークとティントの色も `icon.json` に書いてあります。ダークでは背景をシステムの暗い色にし、「て」を水色、しおりを明るいオレンジにします。ティントでは「て」を白、しおりを灰色にし、色はシステムが付けます。

`Tenabuku/` は同期フォルダなので、`AppIcon.icon` は置くだけでターゲットに入ります。アプリのアイコンの名前（`AppIcon`）とファイル名が同じなので、設定も要りません。iOS 26 より前の OS に向けた平らなアイコン（ダークとティントも）は、ビルドのときに Xcode がこのデータから作ります。

「て」の字は M PLUS Rounded 1c ExtraBold（SIL Open Font License）の字形をパスにしたものです。書き出すときにフォントは要りません。

図柄は Icon Composer（Xcode 26 以降に付属）で `AppIcon.icon` を開いて直します。層の SVG（`AppIcon.icon/Assets/`）を直接書き換えてもかまいません。座標は 1024×1024 で、角丸の枠はありません。

## テスト

テストは `Packages/TenabukuKit/Tests` にあり、アプリ本体にはありません。確かめていることは次のとおりです。

- SHA-1 と HMAC-SHA1 が既知の値と一致すること（RFC 2202 ほか）
- OAuth の署名が RFC 5849 の例と一致すること。はてなに送るリクエストの署名は、Python の標準ライブラリで別に計算した値と比べています
- 各 API が組み立てる URL、メソッド、フォームの中身
- タグの一覧を、配列と `{"tags": [...]}` のどちらの形でも読めること
- タグを 10 個より多く付けられないこと。空のタグと重複を足さないこと
- タグの候補の絞り込みと並び順
- RSS と JSON の読み取り。想定外の形を `parseFailed` として報告すること
- 404 や 401 などのステータスの扱い
- マイホットエントリーの JSON の読み取り。0 件を仕様の変更とみなさないこと、403 を「ログインが要る」として扱うこと、Cookie がなければ問い合わせないこと。送る Cookie を、ドメイン、パス、期限で絞ること
- 非表示ユーザーの一覧の読み取り。`cursor` で続きを読むこと、同じ `cursor` が返ったら止めること、403 を「ログインが要る」として扱うこと、Cookie がなければ問い合わせないこと
- スターのパーマリンクを日本時間の日付で組み立てること。注目と新着のコメントからパーマリンクを取ること。まとめられた数を数に入れること。色付きのスターを色ごとに数えること。スターのないコメントを 0 個とすること。20 個ずつに分けて求めること。数を読むときに Cookie を送らないこと
- 記事の画像の URL を `/api/entry/info` の `image` から読むこと。`image` が空のときと 404 のときに画像なしとすること。想定外の形を `parseFailed` として報告すること
- 記事のページの `og:image` を読むこと。`twitter:image` より `og:image` を選ぶこと。属性の順番、大文字と小文字、引用符の違いを問わないこと。相対 URL を記事の URL から組み立てること。日本語のファイル名をエンコードし、エンコード済みの部分はそのままにすること。`&amp;` などの文字参照を戻すこと。`<body>` の中のタグと、`http` と `https` 以外の URL を使わないこと。64KB より後ろに書かれた画像を読まないこと
- ページの先頭だけを受け取るときに、`</head>` の直後か上限の長さで止めること。`</head>` の大文字と小文字を問わないこと
- スターの付与で、`rks` を読んでから Cookie と一緒に送ること。Cookie がないときに問い合わせないこと。`rks` が `null` のときと `is_guest` が返ったときを「ログインが要る」として扱うこと。`errors` を理由として返すこと
- 自分のブックマークの一覧で、`https` と `http` の検索を新しい順に 1 本にまとめること。2 つの検索を同時に求めること、片方の次のページを待つこと、両方に当たったものを 1 回だけ並べること、10,000 件目で止まること。検索で、続きを読む位置、同じ URL を 2 回並べないこと、空のページで止まること。どちらでも、編集と削除を手元の一覧に反映すること。編集したときに、タグをコメントの先頭に `[タグ]` の形で組み立て直すこと。全文検索の応答から `eid` を読むこと。コメントの先頭のタグを本文から分けること。保存した一覧を読み戻すと、続きを読む位置も戻ること。別のアカウントの一覧を使わないこと、ログアウトで消すこと、前の形式で保存した一覧と読めないファイルを無視すること
- サイトのアイコンの URL を、記事の URL から組み立てること。記事の URL のクエリと `#` もエンコードすること。DuckDuckGo にはドメインだけを、Google には記事の URL を送ること。`http` と `https` 以外の URL ではアイコンを求めないこと
- アイコンの取得先に、選んだ順番で問い合わせ、見つかったところで止めること。はてなが 404 を返したときと、灰色の画像を 200 で返したときに、次へ進むこと。どこも 404 ならアイコンなしとすること
- 取得先の設定で、最初の設定が「はてな → Google」で DuckDuckGo がオフなこと。オンとオフの切り替え、SwiftUI の `onMove` と同じ並べ替え、保存と読み戻し、知らない取得先を読み飛ばすこと
- 日時を `2026-01-02 01:02` の形で、24 時間表示で組み立てること。渡したタイムゾーンで組み立てること
- 既読の記録で、30 日より古いものが消えること。開き直すと残ること。ファイルへの保存と読み込み
- 棚の設定で、最初はすべての棚をはてなのカテゴリーの順に出し、マイホットエントリーを最後に置くこと。出さない棚が順番の中の位置を保つこと。SwiftUI の `onMove` と同じ並べ替え。保存と読み戻し。フィードの URL の名前で保存すること。知らない棚を読み飛ばし、足りない棚を出す状態で末尾に足すこと
- ミュートの条件の読み方。ドメインとサブドメイン、URL の先頭、ワイルドカード、正規表現、大文字と小文字・全角と半角の扱い
- 空の条件と読めない正規表現を見分けること。1,000 個の条件でも一致を見つけること。ファイルへの保存と読み込み、読めないファイルをよけること

テストの入力は 2026 年 10 月に実際に取得した応答の構造をまねて、中身を作り替えたものです。実際の応答は含めていません。

テストで確かめられないことは、次のとおりです。

- はてなが今も同じ形で応答するかどうか。これはアプリを使っていて赤い表示が出たときに分かります
- OAuth の認可の流れ全体と、ログインが要る API の実際の応答
- Keychain への保存と読み込み
- Web のログインの流れと、WebKit の保存場所からの Cookie の取り出し
- スターの付与がはてなで実際に通ること。下の「手で確かめること」で確かめます
- 画面の見た目と操作。一覧で既読のタイトルが薄くなることと、ミュートした記事が一覧から消えることも、ここに含みます
- 全文検索 API が今も新しい順に返すことと、10,000 件目までしか読めないこと。変わっても赤い表示は出ないので、下の「手で確かめること」で確かめます

## iPhone Duo への対応

画面を作るときは、いつも iPhone Duo を意識します。Apple が勧める作り方に沿っていれば、Duo でも大きく崩れません。具体的には、次のことを守ります。

- レイアウトは、機種や画面の向きではなく、サイズクラスと実際に使える大きさで決めます。内側のディスプレイでは、`UISupportedInterfaceOrientations` の縦向きの指定は効きません
- バーは `NavigationStack` の `.toolbar` で作ります。ボタンにはタイトルとシンボルの両方を付けます（`Label` など）。自分で配置したバーは、Duo の縦向きのレイアウトに参加しません
- ボタンなどの操作できるものはセーフエリアの内側に置きます。背景のように全面に広げるものだけ、セーフエリアの外に出します。セーフエリアは左右で幅が違うことがあるので、片側の値を 2 倍して計算しません
- シートやアラートなど、標準の部品を使います。標準の部品は、Duo の姿勢に合わせて表示が変わります

バーが縦に並ぶかどうかで置き場所を変えたいときは、機種ではなく SwiftUI の環境値 `toolbarVerticalEdge` で見分けます。iOS 27.1 から使える値で、バーを縦に置くことのない環境では `nil` になります。

### ボタンの置き場所

各画面のボタンは次の 2 つのレイアウトに分けて置きます。

- 通常の iPhone と、Duo の内側のディスプレイの縦持ち: バーは画面の上と下にあります。よく使うボタンは指の届く下のバーに置きます
- Duo の外側のディスプレイと、内側のディスプレイの横持ち: 縦のバーが画面の右にあります。ボタンは縦のバーに置きます

内側のディスプレイの横持ちでは、完全に開いた状態と半分折りたたんだ状態を区別しません。

ブラウザだけは内側のディスプレイの横持ちを 3 つ目のレイアウトとして分けます。縦のバーとステータスバーを止め、ボタンを下のバーに並べて、ページを画面いっぱいに出します。iOS の Safari と同じく、ページに画面の幅をすべて使わせるためです。Web コミックのように、内容の中心が画面の中央に来てほしいページがあります。

| 画面 | iPhone と内側の縦持ち | 外側と内側の横持ち |
| --- | --- | --- |
| ホーム | 設定は見出しと同じ高さの右端、マイブックマークは下の中央 | 設定は上の右端、マイブックマークは縦のバーの上 |
| マイブックマーク | 戻るは下の左、その右に検索欄 | 戻るは縦のバーの上、検索は縦のバーの下 |
| ブラウザ | 下の左に戻るとページの戻る・進む、右にブコメ、ブクマ、共有。Duo の内側では、その右に全画面。ブクマ数が 1 件以上あれば、ブコメのボタンにその数をバッジで出す。下にスクロールすると隠れ、上にスクロールすると出る | 外側では、縦のバーの上に戻るとページの戻る・進む、下に残りのボタン。内側の横持ちでは、iPhone と同じ下のバー。下にスクロールすると隠れ、上にスクロールすると出る。ステータスバーと上のバーは出さない |
| コメント | 上の左にブクマ数、右に注目と新着の切り替え。下の左に閉じる、右にブクマと Safari で開く。スクロールしても隠れない | 外側では、ブクマ数と切り替えは上に残り、閉じる、ブクマ、Safari で開くが縦のバーに入る。内側の横持ちでは、iPhone と同じ下のバー |

ほかの画面もこの分け方に沿って作ります。分け方から外れる画面を作るときは、その必要があるかを先に確かめます。

置き場所は次のように実現しています。

- ホームとマイブックマークでは、`toolbarTitleDisplayMode(.inlineLarge)` で大きな見出しをバーの行に入れています。こうすると、見出しの上に空いた行が残りません。ホームの設定は見出しと同じ高さに並びます
- ホームの設定はツールバーの項目に iOS 27.1 からの `axisBehavior(.horizontalOnly)` を付け、縦のバーに入れずに上に残しています
- 戻るボタンを下に置く画面では、標準の戻るボタンを隠し、自前の戻るボタンを下のバーに置きます。標準のボタンを隠すと、UIKit は画面の左端からのスワイプで戻る操作も止めます。そこで、スワイプのジェスチャーの delegate を差し替え、戻るボタンを隠した画面でもスワイプが始まるようにしています。差し替えた delegate は元の delegate に問い合わせを回しません。回すと、UIKit の非公開の問い合わせに元の delegate が「受け付けない」と答え、スワイプが始まらないためです
- ブラウザの下のバーでは、iOS 26 からの `ToolbarSpacer(.fixed)` を戻るボタンとページの戻る・進むのあいだに置き、別々のボタンとして描いています。標準の戻るボタンと同じ見え方にするためです
- マイブックマークの検索欄を下のバーに置くのは、iOS 26 からです。iOS 25 以前では、戻るボタンも上に置いたままにします
- ブラウザの内側の横持ちでは、iOS 27.1 からの `toolbarVerticalBehavior(.disabled)` で縦のバーを止めます。止めると `toolbarVerticalEdge` も `nil` になるので、そのまま見分けに使うと、縦のバーを止めたり戻したりを繰り返します。そこで、いったん全画面にしたら、画面が横長でなくなるまで全画面のままにします。横長かどうかはページの表示領域の幅と高さで見分けます。縦に持ち替えたときと閉じたときに、横長でなくなります。上のバーとステータスバーは `toolbar(.hidden, for:)` と `statusBarHidden` で隠します
- コメントの画面では、ブクマ数と注目・新着の切り替えを、ナビゲーションバーではなく、画面の上の自前の行に置いています。ナビゲーションバーに置くと、ブクマ数が大きな見出しになり、切り替えも太いガラスの見た目になるためです。ブクマ数はバーのタイトルと同じ大きさの文字、切り替えは標準の細いセグメントにしています。高さはそのままに、幅を 176pt にしています。1 つの項目が 88pt になり、Apple が求める 44pt の押せる大きさの 2 倍あるので、押しやすくなります。ブクマ数は、文字の枠ではなく見えている字形で縦位置を決め、ベースラインを切り替えの漢字の下端にそろえています。ブクマ数は数字と「users」だけで下に伸びる字がないので、枠の中央で揃えると、漢字より約 1pt 高く見えるためです。文字の大きさを変えても崩れないよう、ずらす量はフォントの寸法と `@ScaledMetric` で決めます。行は iOS 26 からの `safeAreaBar` で置き、上端のスクロールの効果を `scrollEdgeEffectStyle(.soft, for: .top)` にしています。こうすると、システムのバーと同じく、下を流れるコメントがぼけて消え、行の下に線が出ません。ナビゲーションバーは隠します。閉じる、ブクマ、Safari で開くは下のバーに出て、Duo の外側では縦のバーに入ります。内側の横持ちでは `toolbarVerticalBehavior(.disabled)` で下に残します
- コメントの画面は、画面の高さの 94% で開きます。iOS 26 のシートは、画面いっぱいより低い間だけ Liquid Glass で描かれ、いっぱいまで広げると不透明になって画面の端に付くためです。ノブは `presentationDragIndicator(.visible)` で出します。一覧の背景は透明にして、シートのガラスを見せます
- コメントの行の余白は、上下とも 16pt、日時の上は 8pt です。8pt の刻みにそろえています。最初のコメントの上には線を出しません
- 注目と新着は横に並べたページにして、左右のスワイプでも切り替えでも、隣のページが横から入ってくるようにしています（`ScrollView` の `paging`）。`TabView` のページ表示では、切り替えを押してもページが動かないことがありました。ページはバーの裏まで広げ、バーの大きさを各一覧に安全領域として渡します。こうすると、コメントがバーのガラスの裏まで続き、最後のコメントはバーの上までスクロールできます。ページの幅をシートの幅いっぱいにするのは、Duo の外側で縦のバーの横に隣のページの端が見えないようにするためです
- ブラウザの下のバーは、読む人が指でページを下へ 24pt 以上動かすと隠し、上へ動かすかページの一番上に戻ると出します。ページが自分で動いたときは変えません。iPhone でも Duo の内側でも、下にバーがあるときはいつもこうします

アプリ内ブラウザは、この方針で縦の表示領域を確保しています。バーは `.toolbar` で作り、ナビゲーションのタイトルは出しません。Duo の外側のディスプレイではボタンが縦に並ぶので、タイトルを出さなければ、記事が画面の上から下まで使えます。`SFSafariViewController` を使わないのは、「ブコメを見る」などの独自のボタンを置けないためです。

`WKWebView` は上下左右ともセーフエリアの外に広げ、画面いっぱいに置きます。Safari と同じく、スクロールバーを縦のバーの外側の、画面の右端に出すためです。ページは、左右のセーフエリアを `obscuredContentInsets` で WebKit に渡して、縦のバーの手前に収めます。`WKWebView` をセーフエリアの外に広げただけでは、ページの `viewport-fit` の指定や CSS によっては、ヘッダーやページ全体が縦のバーの下に入ります。スクロールバーの上と下は、画面のセーフエリアの分だけ空けて、画面の角の丸みを避けます。

上の余白はページを実際に覆っているものの分だけにします。画面の上のセーフエリアと、高さのあるナビゲーションバーです。Duo の内側のディスプレイでは、ナビゲーションバーが横の列に移っても、高さが 0 のバーが上に残り、その分がセーフエリアに数えられます。そのままだと、`viewport-fit=cover` を指定していないページでは、WebKit が固定ヘッダーをその下に置き、ヘッダーの上の隙間に本文がスクロールして見えます。余白は iOS 26 からの `obscuredContentInsets` で WebKit に渡します。スクロールビューの `contentInset` だけを変えても、固定ヘッダーの位置は変わらないためです。iOS 18 以前では、これまでどおりセーフエリア全体を空けます。読み込み中のバーもセーフエリアではなく、この余白の下端に置きます。左右はセーフエリアを越えて、画面の幅いっぱいに出します。余白はナビゲーションバーの大きさが変わったときにも計算し直します。Duo では、画面を開いた直後にバーの高さが 0 になっても `WKWebView` のセーフエリアは変わらないので、そのままだと最初の値が残り、ページとバーが 24pt 下がったままになります。

下の余白は `obscuredContentInsets` で WebKit に渡さず、スクロールビューの `contentInset` だけで空けます。こうすると、ページは下のバーの裏まで続き、ページの終わりはバーの上までスクロールできます。`contentInset` に入れるのはバーの高さだけで、ホームインジケーターの分は入れません。入れると、ページの終わりまでスクロールしたときに、ページの下端に固定した要素がその分だけ画面の下の端から浮き、その下にページの背景が帯になって見えます。WebKit に下の余白を渡さないのは、ページの下端に固定した要素の色で WebKit がその余白を塗りつぶすためです。GIGAZINE の記事では、広告の枠の灰色が下のバーの裏とホームインジケーターの下を覆い、ページがバーの手前で切れて見えました。代わりに、ページの下端に固定した要素はバーの裏に入ります。下にスクロールすると下のバーが隠れるので、そのときに見えます。

### ブラウザの全画面

Web マンガを画面いっぱいに出す方法は 2 つあります。

1 つ目はページが自分で全画面にする場合です。`WKPreferences.isElementFullscreenEnabled` を `true` にして、ページが Fullscreen API（`requestFullscreen`）を使えるようにしています。既定は `false` で、そのままだと `document.fullscreenEnabled` が `false` になります。そうなると、サイトは全画面のボタンを隠すか、ページの中だけで拡大します。ページの中だけの拡大では、`WKWebView` の大きさまでしか広がらず、下のバーに隠れます。全画面になると、WebKit は `WKWebView` をアプリの画面から外し、専用のウィンドウに移します。そのため、バーもステータスバーも上には出ません。下へのスワイプかページのボタンで全画面を終えると、元の場所に戻ります。comic-days.com の「全画面」はこの方法で広がります。

2 つ目は読む人がバーを隠す場合です。championcross.jp のビューアーは、サイトの設定で全画面のボタンを出していません。「拡大」はページの中だけで広げるので、下のバーに隠れます。そこで、Duo の内側の画面では、下のバーの「全画面」で、上と下のバー、縦のバー、ステータスバーを隠します。隠しているあいだは、ページを画面の下の端まで出します。ホームインジケーターの分を空けたままにすると、画面いっぱいに広がるビューアーの下に、ページの背景が帯になって残るためです。

画面の向きを変えるか Duo を閉じると、バーを戻します。どちらもウィンドウの大きさが変わるので、それで見分けます。ページの大きさで見分けないのは、バーを隠すとページの大きさも変わるためです。

「全画面」を出すのは、Duo の内側の画面だけです。内側の画面は縦持ちでも横持ちでも、下のバーにボタンをもう 1 つ置ける幅があります。iPhone と Duo の外側の画面では、全画面にしたい場面が少なく、バーを戻す方法も一覧に戻ることしかなくなります。内側の画面かどうかは、iOS 27.1 からの `UIHingeInteraction` で、ヒンジが開いているかで見分けます。機種ではなく、ページが置かれた状況で見分けるためです。ヒンジのない iPhone は閉じているものとして扱います。

Duo の外側のディスプレイでは、スクロールでバーを隠す動きは入れていません。バーが横にあるので、隠しても縦の領域は増えず、読んでいる途中で記事の折り返しが変わるだけです。

## 手で確かめること

アプリを変えた Pull Request では、シミュレーターか実機で次を確かめます。iPhone Duo のシミュレーターでは、閉じた状態と開いた状態の両方で確かめます。

- ホームに、ホットエントリーの全カテゴリーの棚が並ぶこと。棚を横にスワイプすると、3 件ずつ続きが出て、ページの端で止まること。次のページの端が右に見えること。Duo の内側の画面では、縦持ちでも横持ちでも 2 ページが並ぶこと
- 設定の「表示する棚」で、チェックを外した棚がホームから消え、並べ替えた順番がホームに出ること。1 行をドラッグすると、その行だけが動くこと。アプリを開き直しても、そのままのこと。「最初の状態に戻す」で元に戻ること
- 棚の記事を開いて戻ると、その棚の記事が読み直されずにすぐ出ること。ホームを下に引くと、読んだ棚が読み直されること
- ホームの棚で行を長押しすると、その行が持ち上がってプレビューとメニューが出ること。プレビューの外をタップして閉じると、行が元の絵のまま戻ること
- エントリーをタップすると、記事がアプリ内ブラウザで開くこと
- ブラウザの「ブコメを見る」のボタンに、一覧に出ていたのと同じブクマ数がバッジで付くこと。iPhone の下のバーでも Duo の外側の縦のバーでも付くこと
- ブラウザの「ブコメを見る」で、注目と新着のコメントが表示されること。注目は、はてなのエントリーページの注目コメントと同じ顔ぶれと順番になること
- コメントの画面が、iPhone でも Duo の外側でも画面のほぼいっぱいに、ノブの付いたガラスのシートで開くこと。最初のコメントの上と見出しの下に線が出ないこと。ブクマ数と注目・新着の切り替えが上の同じ行に並び、ブクマ数の下端と切り替えの文字の下端がそろうこと。iPhone と Duo の内側では、閉じる、ブクマ、Safari で開くが下のバーに出て、スクロールしても隠れないこと。Duo の外側では、それらが縦のバーに出ること。左右にスワイプしても切り替えを押しても、隣のページが横から入って切り替わること。上下にスクロールしても切り替わらないこと。新着を最後までスクロールすると、最後のコメントが下のバーに隠れないこと。各コメントの 1 行目に ID、本文、タグが続けて並び、その下に日時とスターが並ぶこと。日時とスターの数が `2026-01-02 01:02` の形の等幅の文字で出て、どの行でもスターの左端がそろうこと。星が日時の文字より下にずれず、日時と同じ高さに並ぶこと。コメントの上下の余白が同じで、日時の上に少し間が空くこと。閉じるでコメントの画面が閉じること
- コメントの画面の「Safari で開く」で Safari が開くこと
- 設定の「はてなでログイン」で承認ページが開き、許可すると、はてな ID が表示されること。アプリを開き直してもログインしたままのこと
- ブラウザ、コメントの画面、一覧の長押しメニューのそれぞれから、ブックマークの画面が開くこと
- コメント、タグ、非公開を付けて保存でき、もう一度開くとその内容が入っていること。削除できること
- タグの入力に合わせて、候補が絞り込まれること。11 個目のタグを足せないこと
- 設定でログアウトすると、ブックマークの画面がログインを求めること
- ブラウザの「共有」で共有メニューが開くこと
- comic-days.com のエピソードで、ビューアーの「全画面」を押すと、バーとステータスバーの上までマンガが広がること。下にスワイプすると、元のブラウザに戻ること
- Duo の内側の画面で、championcross.jp のエピソードのビューアーの「拡大」を押してから、ブラウザの「全画面」を押すと、バーとステータスバーが消えて、ビューアーが画面の下の端まで広がること。画面の向きを変えるか Duo を閉じると、バーが戻ること。iPhone と Duo の外側の画面では、「全画面」が出ないこと
- 記事を開いて一覧に戻ると、そのタイトルが薄くなること。アプリを開き直しても薄いままのこと
- 一覧の設定で「既読の記録を消す」を押すと、すべてのタイトルが元の濃さに戻ること
- 一覧のエントリーを長押しして、メニューの「ミュート」を押すと、ドメインが入ったミュートの画面が開くこと。保存すると、同じドメインの記事が一覧から消え、一覧の末尾に隠した件数が出ること。アプリを開き直しても消えたままのこと
- ミュートの画面で「タイトル」に切り替えると、入力がエントリーのタイトルに変わること。読めない正規表現では赤い表示が出て、保存できないこと
- 設定の「ミュートの条件」で、条件を編集・削除できること。削除すると記事が一覧に戻ること
- iPhone と Duo の内側の縦持ちでは、ホームの設定が「ホットエントリー」の見出しと同じ高さの右端に、マイブックマークのボタンが下の中央に出ること。Duo の外側と内側の横持ちでは、設定が上の右端に、マイブックマークのボタンが縦のバーの一番上に出ること
- iPhone と Duo の内側の縦持ちでは、マイブックマークの戻るボタンが下の左に、検索欄がその右に出ること。見出しの上に空いた行がないこと。戻るボタンでも、画面の左端からのスワイプでも、ホームに戻ること。Duo の外側と内側の横持ちでは、戻るボタンが縦のバーの上に、検索が縦のバーの下に出ること
- iPhone と Duo の内側の縦持ちでは、ブラウザの下のバーの左に、戻るボタンとページの戻る・進むが出て、右に残りのボタンが出ること。戻るボタンでも、画面の左端からのスワイプでも、一覧に戻ること。Duo の外側では、縦のバーの上に戻るボタンとページの戻る・進むが出て、下に残りのボタンが出ること。Duo の内側の横持ちでは、ステータスバーと上のバーが出ず、ページが画面いっぱいに出ること。ボタンは iPhone と同じく下のバーに出ること。iPhone と Duo の内側では、下にスクロールすると下のバーが隠れ、上にスクロールすると出ること。Duo の外側では、スクロールしても縦のバーが隠れないこと。ブラウザを開いたまま持ち替えたり閉じたりすると、そのレイアウトの置き場所に移ること。一覧に戻ると、縦のバーが元に戻ること
- ホームのマイブックマークのボタンが、ログインしているときは自分のプロフィール画像に、ログインしていないときは人の形のアイコンになること。ログアウトすると人の形に戻ること
- 一覧の「マイブックマーク」で、自分のブックマークが非公開のものも含めて、新しい順に表示されること。鍵の印が非公開のものに付くこと。URL が `http://` で始まるブックマークも出ること
- マイブックマークの各行で、左にサイトの行とタイトルが、右に記事の画像が出ること。タイトルが 3 行まで出て、それより長いと 3 行目の終わりが「…」になること。画像のない記事では、地球の印が出ること。記事の下に、自分のプロフィール画像、ブックマークした日時、スターの数が 1 行に並ぶこと。日時とスターはコメントの画面と同じ形と高さで出ること。その下に、日時と左をそろえて、コメントとタグが行の幅いっぱいに出ること。タグの前に `#` が付かないこと。コメントもタグもないブックマークでは、プロフィール画像と日時の行だけが出ること。開いたことのある記事でも、タイトルが薄くならないこと。ID は出ないこと。設定の「自分のアイコンを出す」をオフにすると、プロフィール画像が人の形のアイコンになること。行の右に `>` が出ないこと
- マイブックマークで、スターの付いた自分のコメントの日時の横に、はてなのサイトと同じ数のスターが出ること。色付きのスターが色ごとに黄色のスターの前に出ること。星を押しても何も起きず、行のタップで記事が開くこと
- マイブックマークの一覧を下までスクロールすると、続きが読み込まれること
- マイブックマークの一覧を開き直すと、すぐに一覧が出ること。下に引っ張ると、読み込んだ時刻が新しくなること。ログアウトしてログインし直すと、一覧を読み直すこと
- マイブックマークで検索すると、タイトル、本文、URL、コメントに言葉を含むものが並ぶこと。検索欄を空にすると一覧に戻ること
- マイブックマークの行をタップすると記事が開くこと。長押しメニューの「編集」から保存すると行のコメントが変わり、削除すると行が消えること
- ログアウトした状態でマイブックマークを開くと、ログインを求められること
- ホームに「マイホットエントリー」の棚があること。Web でログインしていない状態では、その棚にログインを促す表示が出ること
- そこからログインすると、シートが閉じて、はてなの Web と同じ記事が棚に並ぶこと。既読のタイトルが薄くなり、ミュートした記事が隠れること。アプリを開き直しても、ログインしたままのこと
- 設定の「はてなの Web」でログアウトすると、マイホットエントリーがログインを求めること
- コメントの画面で、注目と新着のどちらにもスターの数が出ること。はてなのエントリーページと同じ数になること。色付きのスターが色ごとに黄色のスターの前に出ること
- Web でログインした状態で星を押すと、数が 1 つ増えること。はてなのエントリーページでも、そのスターが見えること
- Web でログアウトした状態で星を押すと、ログインの画面が出ること。ログインすると、そのスターが付くこと
- Web でログインした状態で、はてなで非表示ユーザーにした人のコメントがあるエントリーを開くと、その人のコメントが注目と新着のどちらにも出ないこと。Web でログアウトすると、その人のコメントが出ること
- ホットエントリーとマイブックマークの一覧で、タイトルの上の行に、サイトのアイコンとドメインが左に、ブックマーク数が右端に出ること。アイコンがはてなブックマークの Web と同じになること。`musica-terra.com/interactive/modal-earth/` のように、はてなが変換できない SVG のアイコンも、ブラウザと同じものが出ること。設定の「サイトのアイコン」で取得先を切り替えたり並べ替えたりすると、一覧のアイコンが読み直されること。VoiceOver ではタイトルが先に読まれること
- ホットエントリーとマイブックマークの一覧とホームの棚で、記事の画像が正方形のまま、上端がサイトの行の上端に、下端がタイトルの 3 行目の下端にそろうこと。設定の「画面表示と明るさ」で文字を大きくしても、そろったままのこと
- ホットエントリーで、はてなに画像がない記事（`og:image` が WebP や AVIF のページなど）にも、記事の画像が出ること。ページに画像がない記事では、地球のアイコンが出ること
- ホットエントリーとマイブックマークの一覧をすばやくスクロールしたとき、新しく画面に入った行のアイコンと記事の画像が、1 つずつ遅れて出ずに最初から出ていること
- ホームを何棚か下へスクロールしてから上に戻ったとき、最初の棚の記事の画像が空の枠を挟まずに最初から出ていること。横長の画像が切り出す前と同じ部分を見せていること
- ホットエントリーとマイブックマークの一覧で行を長押しすると、記事のプレビューとメニューが出ること。読み込み中は、サイト名とタイトルが出ること。プレビューをタップすると記事が開き、ページを読み直さないこと
- 長押しのプレビューを入れたあとも、行のタップで記事が開き、一覧をスクロールできること
- Duo の外側では、ブラウザのスクロールバーが縦のバーの右の、画面の右端に出ること。ページとページの固定ヘッダーは縦のバーの手前に収まり、縦のバーの下に入らないこと
- GIGAZINE の記事のように、ページの下端に広告を固定したページを開くと、どの状態でも、ページが下のバーの裏と画面の下の端まで続き、その部分が灰色で塗りつぶされないこと。はてな匿名ダイアリーの記事のように、下端に広告を固定したページを最後までスクロールしても、広告が画面の下の端に付いたままで、その下に帯が出ないこと
- Duo の開いた状態で、note.com のように `viewport-fit=cover` を指定していないページを開いてスクロールすると、固定ヘッダーが画面の上端に付き、その上に本文が見えないこと。iPhone と Duo の閉じた状態では、固定ヘッダーがナビゲーションバーの下に出ること。読み込み中のバーが、どの状態でもページが見える範囲の上端に、画面の幅いっぱいに出ること

## バージョン

バージョンは `project.yml` の `MARKETING_VERSION` です。配布はしていないので、リリースの手順とバージョンの上げ忘れを止める CI はありません。
