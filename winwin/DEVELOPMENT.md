# winwin の開発

winwin をビルド・変更するための情報です。使い方やインストール方法は [README.md](./README.md) を参照してください。

Windows 版は Rust で書いた単一の exe です。常駐部分は [`windows`](https://crates.io/crates/windows) クレート(Win32 API の
バインディング)だけで組み、設定画面は [`windows-reactor`](https://crates.io/crates/windows-reactor)(Rust から WinUI 3 を
使う Microsoft のクレート)で組んでいます。WinUI 3 を動かす Windows App Runtime は exe と同じフォルダに置いて配布します
(self-contained)。GitHub Actions の `windows-latest` でビルドし、[NSIS](https://nsis.sourceforge.io/) でインストーラを
作ります。macOS 版は、同じ Rust のライブラリを Swift のアプリから呼びます(「macOS 版」の節)。配布するのは
Windows (x64) と macOS (Apple シリコン) です。

## 開発に必要なもの

| ツール | 備考 |
|---|---|
| [Rust](https://rustup.rs/)(stable、1.95 以降) | `rustup` でインストール。`windows-reactor` が 1.95 以降を求めます |
| Windows: Visual Studio Build Tools | 「C++ によるデスクトップ開発」を選択。Rust は MSVC ツールチェーンを既定にする |
| [NSIS](https://nsis.sourceforge.io/) 3 | インストーラを作るときだけ。`makensis` が使えればよく、Linux のパッケージでも構いません |
| [PowerShell](https://learn.microsoft.com/powershell/) 7(`pwsh`) | インストーラを作るときだけ。同梱するファイルの一覧を書き出します |

Windows でのビルドは、初回に Windows App Runtime のパッケージを nuget.org からダウンロードします(`build.rs` が呼ぶ
`windows-reactor-setup`。`%LOCALAPPDATA%\windows-reactor-setup` にキャッシュされます)。

Windows 以外でも、Win32 に触れない部分(設定ファイル・配置の計算・ショートカットの表記・設定画面の編集中データ)は
そのままビルド・テストできます。Win32 側の型検査は `x86_64-pc-windows-msvc` ターゲットで行えます(リンクはできません)。

```sh
rustup target add x86_64-pc-windows-msvc
cargo clippy --target x86_64-pc-windows-msvc --all-targets -- -D warnings
```

## ビルドと実行

```sh
cd winwin
cargo run                   # デバッグビルドで起動(コンソールが開き、終了はトレイメニューから)
cargo run -- --settings     # 設定画面だけを起動
cargo build --release       # 配布用ビルド: target/release/winwin.exe と、横に置かれる Windows App Runtime
```

インストーラ(`installer/installer.nsi`)は、リリースビルドのあとに同梱するファイルの一覧(`payload.nsh`)を書き出してから
作ります。一覧は exe と、`target/release` に置かれた Windows App Runtime のファイルです。

```sh
cd winwin/installer
pwsh payload.ps1 -Dir ../target/release -Out payload.nsh
makensis /INPUTCHARSET UTF8 /DVERSION=0.6.0 /DPAYLOAD=payload.nsh /DOUTFILE=../target/release/winwin_0.6.0_x64-setup.exe installer.nsi
```

デバッグビルドはコンソールサブシステムで、リリースビルドだけがコンソールを持たない GUI サブシステムです
(`src/main.rs` の `windows_subsystem`)。

## 検証コマンド

```sh
cargo fmt --check
cargo clippy --all-targets -- -D warnings
cargo test
```

CI(`.github/workflows/winwin.yml`)は `windows-latest` でこの 3 つとリリースビルド、インストーラの作成を実行します。

## Pull Request のビルド

`winwin/` を変更する Pull Request では、GitHub Actions が Windows 版と macOS 版をビルドし、Windows 版が成功すると
インストーラへのダウンロードリンクを Pull Request にコメントします。macOS 版も成功していれば、`.dmg`(Apple シリコン用)
へのリンクも並べます。push のたびに新しいコメントを投稿し、前回までのコメントは outdated として畳みます。
リンク先のダウンロードには GitHub へのログインが必要で、成果物には保持期限があります(期限はコメントに書かれます)。

## macOS 版

ライブラリを静的ライブラリ(`libwinwin.a`)としてビルドし、[UniFFI](https://github.com/mozilla/uniffi-rs) 0.32 が
`ffi.rs` と `ffi/settings.rs` から書く Swift のバインディングを通して、Swift のアプリ(`macos/`)から呼びます。
アプリが受け持つのは、メニューバーのアイコン、イベントタップ(`CGEventTap`)でのキーの受け取り、アクセシビリティ API
(`AXUIElement`)でのウィンドウの測定と移動、SwiftUI の設定画面とテスト用ウィンドウの描画、ログイン時の起動
(`SMAppService`)、アクセシビリティの許可の確認です。どのキーをショートカットとして取るか、どこへ配置するか、
ウィンドウがどの画面にあるか、設定画面の一覧の選択や保存時の検証、リセットで戻す位置・大きさは、ライブラリが決めます。

必要なものは Rust(stable)と Xcode のコマンドラインツール(Swift 5.9 以降)で、macOS 13 以降で動きます。

```sh
winwin/macos/build.sh       # winwin/macos/winwin.app ができる
open winwin/macos/winwin.app
```

- 初回起動時に macOS がアクセシビリティの許可を求めます。システム設定で winwin をオンにすると、そのままショートカットが
  使えるようになります
- 設定ファイルは `~/Library/Application Support/winwin/config.toml` です。初回起動時に初期値で作られます
- Command は Win、Option は Alt として扱います(同じ位置のキー)。キーは US 配列での位置で決まり、JIS 配列の ¥ と
  ろは、Windows の JIS 配列と同じく `Oem5` と `Oem102` です。設定画面のキーキャップは、修飾キーを Mac の記号と順
  (⌃⌥⇧⌘)で描きます。ファイルには Windows 版と同じ名前で書きます
- `build.sh` はアプリにアドホック署名をします。ビルドし直すと署名が変わるため、アクセシビリティの許可が外れることが
  あります。そのときは、システム設定の一覧から winwin を削除して、許可し直してください
- アプリのアイコンは、`build.sh` がビルドしたアプリ自身に `--iconset` で書き出させ(Windows 版と同じ `art.rs` の絵)、
  `iconutil` で `.icns` にします

キーの行き先は、そのときの状態で切り替えます(`AppDelegate.swift`)。設定画面を開いている間は、常駐部分のショートカットを
受け取りません(Windows 版が登録を解除するのと同じです)。テスト用ウィンドウを開いている間は、編集中の行でできる
ショートカットがテスト用ウィンドウを動かします。ショートカットを記録するダイアログを開いている間は、winwin が前面に
あるときのキーをすべてダイアログに渡し、ほかのアプリやシステムには渡しません。

リセットで戻す位置・大きさは `restore::Sizes` が覚えます。アクセシビリティ API はウィンドウを尋ねるたびに別の要素を
返しますが、同じウィンドウの要素は比べると等しいので、アプリは要素ごとに番号を振ってライブラリに渡します
(`WindowIDs`)。Windows 版と違って、次のものはまだありません。

- ドラッグで元の大きさに戻す動き。ウィンドウの移動を見張る仕組み(`AXObserver`)とカーソルを追う処理が要るため、別の
  Pull Request で扱います
- 配置したあとに縁をドラッグして大きさを変えたウィンドウを忘れること。今はリセットすると最初の配置の前に戻ります
- winwin を起動し直したあとも覚えていること。Windows 版はウィンドウプロパティに残しますが、macOS にはほかのアプリの
  ウィンドウに値を残す手段がありません
- 最大化(フルスクリーン)の扱い。最大化していたかどうかは覚えません

CI(`.github/workflows/winwin.yml` の `build-macos`)は `macos-latest` で、feature `ffi` を含めた clippy とテスト、
`build.sh` を実行し、できた `winwin.app` を `/Applications` へのリンクと一緒に `.dmg` にまとめてアップロードします。
アプリは Apple シリコン用だけで、Intel Mac 用のビルドと universal binary は作りません(リポジトリの `CLAUDE.md`)。

```
winwin/
├── build.rs            # Windows App Runtime の配置、アプリケーションマニフェストと exe のアイコンの埋め込み
├── winwin.manifest     # DPI 対応などの宣言。build.rs が Windows App Runtime のマニフェストと合わせて埋め込む
├── installer/
│   ├── installer.nsi   # Windows インストーラ(NSIS)
│   └── payload.ps1     # インストーラに入れるファイルの一覧(payload.nsh)を書き出す
├── macos/              # macOS 版。「macOS 版」の節を参照
│   ├── build.sh        # ライブラリ・バインディング・アプリをビルドし、winwin.app にまとめる
│   ├── Info.plist      # アプリのバンドルの情報。build.sh がバージョンを埋める
│   ├── Package.swift
│   └── Sources/
│       ├── winwinFFI/  # バインディングの C 側(build.sh が書くヘッダーと、静的ライブラリを指す module.modulemap)
│       └── Winwin/
│           ├── AppDelegate.swift # 常駐部分: メニューバーのアイコン、キーの行き先の切り替え、設定画面とテスト用ウィンドウの開け閉め
│           ├── KeyTap.swift      # イベントタップでのキーの受け取り
│           ├── Mover.swift       # 前面ウィンドウの測定と移動、リセット、ウィンドウの番号(WindowIDs)、画面の座標
│           ├── TestWindow.swift  # テスト用ウィンドウ
│           ├── Autostart.swift   # ログイン時の起動(SMAppService)
│           ├── Permission.swift  # アクセシビリティの許可
│           ├── Icon.swift        # アイコンの描画と、build.sh が使う .iconset の書き出し
│           └── Settings/         # 設定画面(SwiftUI)。SettingsModel が ffi/settings.rs の SettingsEditor を包む
└── src/
    ├── main.rs         # Windows アプリの入口。win/ と合わせて bin になる
    ├── lib.rs          # win/ 以外のモジュールをまとめたライブラリ。OS に依存しない
    ├── config.rs       # 設定ファイルの型・読み書き・初期値
    ├── layout.rs       # ショートカットの動作(配置かリセット)、配置(基準位置・幅・高さ、またはフィット)から矩形を求める計算と、プレビュー用に縮めた画面
    ├── hotkey.rs       # ショートカットの表記("Ctrl+Alt+Left")と、OS に依存しないキー・修飾キーの型、設定画面でのキーの記録
    ├── vk.rs           # キー・修飾キーと Windows の仮想キーコード・RegisterHotKey の MOD_* の相互変換
    ├── mac.rs          # macOS のキーイベントのキーコード・修飾キーのフラグから Hotkey への変換と、AppKit の座標の変換
    ├── ffi.rs          # macOS 版が呼ぶ入口(UniFFI)。feature `ffi` のときだけビルドされる
    ├── ffi/settings.rs # macOS 版の設定画面が呼ぶ入口: 編集中の一覧、ショートカットの記録、表示する値
    ├── bin/uniffi-bindgen-swift.rs # ffi.rs から Swift のバインディングを書き出すツール(feature `ffi-bindgen`)
    ├── cycle.rs        # 同じショートカットを持つ項目のまとめ方、押すたびに進む順番、順に押すショートカットの 2 つ目の待ち方
    ├── restore.rs      # 配置したウィンドウの元の大きさ・位置の記憶と、ドラッグで動かしたときやリセットで戻す大きさ・位置
    ├── art.rs          # アイコンの絵(ピクセル)。トレイ・設定画面・exe のアイコンのすべてがこれを描く
    ├── icon_res.rs     # exe に埋め込むアイコンのリソース(.res)を組み立てる。build.rs が使う
    ├── draft.rs        # 設定画面で編集中の一覧(Editor)と 1 行(Draft)。保存時にここで検証する
    └── win/            # Win32 に触れる部分。Windows でだけビルドされる
        ├── app.rs      # 常駐部分: 隠しウィンドウ、メッセージループ、ホットキー、通知領域アイコン
        ├── shortcuts.rs # ショートカットの登録と、押されたときの `cycle.rs` への受け渡し・タイマー(常駐部分とテスト用ウィンドウで共用)
        ├── marks.rs    # 配置したウィンドウに残す、元の大きさ・位置のウィンドウプロパティ
        ├── mover.rs    # 前面ウィンドウの移動、ドラッグ後やリセットで元の大きさへ戻すときの測定と移動
        ├── settings.rs # 設定画面のプロセスの起動・前面化・終了の検知(常駐側)
        ├── settings_ui.rs # 設定画面(WinUI 3。`--settings` で起動したプロセスで動く)
        ├── testwin.rs  # 設定画面から開くテスト用ウィンドウ(設定画面のプロセスで動く)
        ├── autostart.rs# サインイン時の自動起動(レジストリの Run キー)
        └── icon.rs     # 通知領域アイコンの描画
```

`win/` 以外の 11 のモジュールは Win32 に依存しないので、どのプラットフォームでもテストできます。`icon_res.rs` を除く
10 は `lib.rs` がライブラリにまとめ、`main.rs` と `win/` はそれを使う bin です。macOS 版は `ffi.rs` を通して同じライブラリを
使います。挙動を決めるロジックはなるべくライブラリに置き、`win/` と `macos/` は OS との受け渡しに留めています。

キーと修飾キーは `hotkey.rs` の `Key` と `Modifiers` で表し、Windows の仮想キーコードや `MOD_*` には `vk.rs` で
変換します。設定ファイルでは名前のないキーを仮想キーコードで書く(`0xAD`)ため、`vk.rs` は Windows 以外でも使います。

## 設定ファイル

`%APPDATA%\winwin\config.toml` です。初回起動時に初期値で作られ、設定画面の「保存して閉じる」で上書きされます。

```toml
theme = "dark"            # system(既定。書かない)/ light / dark。設定画面とトレイメニューの明暗

[[shortcut]]
keys = "Ctrl+Alt+K"
anchor = "bottom-right"   # top-left / top / top-right / left / center / right / bottom-left / bottom / bottom-right
width = "1/2"             # 作業領域に対する比率。"1/2" のような分数か "0.5" のような小数(0 より大きく 1 以下)
height = "1/2"

[[shortcut]]
keys = "Ctrl+Left, Up"   # 順に押すショートカット
anchor = "top-left"
width = "1/2"
height = "1/2"

[[shortcut]]
keys = "Ctrl+Alt+H"
anchor = "top-left"
width = "keep"            # 押した時点のウィンドウの幅をそのまま使う(height も同じ)
height = "1/3"

[[shortcut]]
keys = "Ctrl+Alt+R"
anchor = "right"
fit = true                # width と height の代わりに。基準位置の側の空きいっぱいに広げる(anchor に center は不可)

[[shortcut]]
keys = "Ctrl+Alt+Backspace"
reset = true              # anchor・width・height の代わりに。最初に配置する前の位置・大きさに戻す
```

- `keys` は `Win` `Ctrl` `Alt` `Shift` と 1 つのキーを `+` でつなぎます。キー名は `hotkey.rs` の表にあるもの
  (`A`〜`Z`、`0`〜`9`、`F1`〜`F24`、`Left` などの名前)か、仮想キーコードの 16 進表記(`0xBA`)です
- `Cmd`(`Command`)は `Win` と、`Option`(`Opt`)は `Alt` と同じに読みます。書き出すときは `Win` `Alt` です
- `Ctrl` `Alt` `Win` のどれも含まないショートカットは受け付けません(`Shift` だけでは、そのキーを全アプリから奪うため)
- 順に押すショートカットは、組み合わせを `,` で区切って 2 つ並べます(`MAX_STROKES`)。どちらにも上の規則が当てはまり、
  修飾キーは同じ、キーは違うものにします。2 つ目は 1 つ目と修飾キーを共有するので、キーだけを書きます(`Ctrl+Left, Up`)。
  修飾キーまで書いても(`Ctrl+Left, Ctrl+Up`)同じに読みます。設定画面の表示も同じく、2 つ目はキーだけです
  (`hotkey::strokes_text`、`hotkey::strokes_caps`)
- 一方がもう一方の途中までと同じショートカット(`Ctrl+Left` と `Ctrl+Left, Up`)も書けます。短い方を押した時点で
  その配置にし、長い方の続きが来ればそちらの配置に置き換えます
- 同じ `keys` を複数の項目に使えます。修飾キーを押したまま(順に押すショートカットでは、2 つ目の組み合わせを)続けて押すと、
  ファイルに書いた順に切り替わります
- `width` `height` の `keep` は、押した時点のウィンドウの見えている枠の幅・高さを使います。最大化中のウィンドウは
  解除したあとの大きさです。作業領域より大きければ作業領域に収めます。設定画面では欄を空にしたときに当たり、
  空の欄には「（幅を維持）」「（高さを維持）」と薄く表示します。一覧では基準位置・幅・高さを行をまたいでそろう列に
  並べ(`左上` `w1/2` `h1`)、維持する方の列は空けます。保存時のエラーで行を示すときは維持する方を書きません
  (`左上 , h1/3`。両方なら基準位置だけ)
- `fit = true` の項目には `width` `height` を書きません(書いてあれば読み捨てます)。`fit` のない項目で `width` か `height` が欠けていると、読み込みエラーになります。設定画面では基準位置の横の「フィット」のチェックボックスで切り替えます。オンのあいだは幅・高さの欄が無効になり、一覧では幅と高さの 2 列に「フィット」と出します
- `reset = true` の項目には `anchor` `width` `height` `fit` を書きません(書いてあれば読み捨てます)。`reset` のない項目で `anchor` が欠けていると、読み込みエラーになります。設定画面では「動作」のラジオボタンで「配置」と「リセット」を切り替えます。リセットのあいだは基準位置・フィット・幅・高さが無効になり、プレビューは画面だけを描きます。一覧では基準位置・幅・高さの 3 列に「リセット」と出します。初期値にはリセットの項目を入れていません
- 書き出すときは、分母 12 以下の分数で表せる値は分数(`2/3`)、それ以外は小数 3 桁に丸めた値(`0.077`)にします。
  丸めると 0 になる小さな値は `0.001` にします(0 は読み込めないため)
- 0.3 までの版は `"50%"` `"800px"` の形で書いていました。`%` は比率に読み替え、読み込んだ時点でファイルを比率で
  書き直します(`33.333%` は `1/3` になります)。`px` は比率に直せないので読み込みエラーになります

ファイルを直接編集した場合、次に設定画面を閉じたとき(保存・キャンセルどちらでも)か、winwin を起動し直したときに
読み込まれます。読み込みに失敗すると、ショートカットを 1 つも登録せずに起動し、エラーをメッセージボックスで伝えます。

## 実装メモ

### 常駐部分はメッセージを待つだけ

グローバルショートカットは `RegisterHotKey` で登録しています。キーボードフックは使わないので、キー入力のたびに
winwin が呼ばれることはなく、ショートカットが押されたときに `WM_HOTKEY` が届くだけです。常駐中のスレッドは
`GetMessageW` で眠っていて、ふだんはタイマーやポーリングはありません。`MOD_NOREPEAT` を付けているので、押しっぱなしでも
1 回しか届きません。

### 切り替え(サイクル)ショートカット

同じ `keys` の項目は `cycle.rs` の `bindings` で 1 つにまとめます。押されたときにどの項目を使うかは `Presses` が決め、
同じショートカットの最後の組み合わせが続けて届くと次へ進みます。登録とタイマーは `win/shortcuts.rs` の `Shortcuts` が
`Presses` に合わせて行い、常駐部分とテスト用ウィンドウが同じものを使います。

`WM_HOTKEY` には修飾キーを離したことが含まれないので、切り替えの途中か続きを待っている間だけ 15ms 間隔のタイマー
(`MODIFIER_TIMER`)を動かし、`GetAsyncKeyState` でその修飾キーを見ます(`Presses::watching`)。どれか 1 つでも離されて
いれば `Presses` を戻してタイマーを止めるので、ポーリングが続くのは修飾キーを押している間だけです。キーボードフックは
使いません。設定画面を開いてショートカットを解除するときも、同じように戻します。

### 順に押すショートカット

`Ctrl+Left, Up` のように、修飾キーを押したまま 2 つのキーを順に押すショートカットも、キーボードフックを使わず
`RegisterHotKey` だけで受け取ります。常に登録しておくのは各ショートカットの 1 つ目の組み合わせだけです
(`cycle::first_strokes`)。1 つ目が押されると `Presses` が続きを待つ状態になり、次に来うる組み合わせ
(`Presses::next_strokes`)を、修飾キーを押している間だけ追加で登録します。修飾キーを離すと `MODIFIER_TIMER` が
追加分を解除するので、他のアプリから組み合わせを取るのは、修飾キーを押し続けている間だけです。

- 2 つの組み合わせは修飾キーが同じで、キーが違うものに限ります(`Keys::new`)。修飾キーを押したまま押すものなので、
  見張る修飾キーは 1 組で済みます。同じキーの 2 連打を認めないのは、切り替えと区別できないためです
- 続きでない組み合わせ(どこかのショートカットの 1 つ目)が来たら、待っていたものを捨ててそちらを最初から扱います
- 押した組み合わせがそれだけでショートカットで、かつ 2 つ押すショートカットの 1 つ目でもあるときは、すぐにその配置に
  したうえで続きを待ちます。`Presses` は「続きを待つ」と「切り替え中」を同時に持てます
- 最後まで押されたショートカットに項目が 2 つ以上あれば、2 つ目の組み合わせを登録したまま次の項目へ進めます。
  その組み合わせが別のショートカット(`Ctrl+Up` 単独など)でもあるときは、修飾キーを離すまで切り替えが優先されます
- 同じ組み合わせを二重に登録すると `RegisterHotKey` が失敗するので、1 つ目として登録済みのものは追加で登録しません。
  ホットキー ID は登録した組み合わせの並び(`Shortcuts::registered`)の位置で、組み合わせから引き直して `Presses` に渡します

設定画面で記録するときも同じで、`Recorder` は修飾キーを押したまま押した 2 つ目のキーを続きとして記録します。
修飾キーを押し直したり離したりしたあとのキーや、3 つ目のキー、同じキーの 2 回目は、記録をやり直します。押しっぱなしの
キーのリピートは、続きとして数えません。

隠しウィンドウは message-only ウィンドウではなく、表示しないトップレベルウィンドウです。Explorer が再起動したときの
`TaskbarCreated` ブロードキャストはトップレベルウィンドウにしか届かず、通知領域アイコンを出し直せなくなるためです。

二重起動は名前付きミューテックスで防ぎます。2 つ目の winwin は 1 つ目の隠しウィンドウに `WM_APP_OPEN_SETTINGS` を
送って終了するので、起動中にもう一度起動すると設定画面が開きます。

### 見えている枠を合わせる

Windows 10 以降のウィンドウは、見えている枠の外側に透明なリサイズ用の縁を持っています。`GetWindowRect` の矩形を
そのまま合わせると隣のウィンドウとの間に隙間ができるので、`DWMWA_EXTENDED_FRAME_BOUNDS`(見えている枠)との差を
縁の幅として足してから `SetWindowPos` します。縁の幅は大きさによって変わることがあるため、動かしたあと枠が
狙いとずれていれば、もう一度だけ測り直して置き直します。

配置の計算(`layout.rs`)は左右・上下の辺を浮動小数のまま求めてから個別に丸めます。幅 1921px を 3 等分しても、
隣り合う配置の辺が同じ位置に揃います。

次のウィンドウは動かしません: 最小化中、表示されていない(トレイメニューを閉じた直後は winwin 自身の隠しウィンドウが
前面になる)、応答なし(`SetWindowPos` が winwin ごと止まるため)、デスクトップとタスクバー。

### フィット

`fit = true` の配置はいちばん手前にあるほかのウィンドウ(以下、前のウィンドウ)を避けて、基準位置の辺から広げられるいちばん大きな矩形に合わせます(`layout::fit`)。前のウィンドウより後ろのウィンドウは数えません。

- 「左」は作業領域の左辺から前のウィンドウの左辺までの幅で、高さは作業領域いっぱいです。「右」「上」「下」も同じ考え方です
- 四隅は横・縦それぞれ、基準位置の辺から前のウィンドウの手前の辺までにします。前のウィンドウがその辺に接している向きは、前のウィンドウと同じ範囲にして横に並べます(右下 2/3×2/3 のウィンドウに対する「左下」は幅 1/3・高さ 2/3)。両方の向きで接していれば角が埋まっているので動かしません
- 前のウィンドウが基準位置の辺に接しているとき(四隅では、横・縦のどちらにも広げられないとき)は動かしません。最大化を解除していたウィンドウは最大化し直します
- 前のウィンドウがないときは作業領域全体です
- 「中央」は広げる辺がないので選べません。設定ファイルで `anchor = "center"` と `fit = true` を一緒に書くと読み込みエラーになり、設定画面ではフィットのあいだ「中央」のボタンを無効にし、基準位置が中央のあいだ「フィット」のチェックボックスを無効にします
- ほかのウィンドウは `EnumWindows` で前面から順に集め、見えている枠(`DWMWA_EXTENDED_FRAME_BOUNDS`)を渡します(`mover::other_frames`)。動かすウィンドウ自身、常に最前面のウィンドウ(`WS_EX_TOPMOST`)、非表示・最小化中・クローク中(別の仮想デスクトップにあるものなど)のウィンドウ、ツールウィンドウ、デスクトップとタスクバーは除きます。前のウィンドウはこのうち作業領域に重なる最初のものです
- 最大化中のウィンドウはそのモニターの作業領域全体として渡します。それが前のウィンドウなら空きはありません
- 設定画面のプレビューは、大きさが前のウィンドウで決まる向きを「維持」と同じく画面の半分として描き、画面端に接していない辺を破線にします。「左」「右」は幅だけ、「上」「下」は高さだけ、四隅は両方です

### ドラッグで元の大きさに戻す

ショートカットで配置したウィンドウをタイトルバーで動かすと、動き出した時点で最初に配置する前の大きさに戻します
(Windows のスナップと同じ)。判断は `restore.rs` の `Sizes` が行い、`win/` はウィンドウの矩形・カーソル・DPI を測って
渡すだけです。

- 配置したとき(`mover::place_foreground` が返す `Placed`)に、配置前の外枠の大きさ・モニターの DPI・配置後の矩形を
  ウィンドウハンドルごとに覚えます。前回 winwin が置いた場所から動いていなければ、配置前の大きさは最初のものを引き継ぐので、
  切り替えショートカットや別の配置を何度続けても、最初の配置の前の大きさに戻ります。最大化中なら、`SW_RESTORE` した後の大きさです
- ドラッグの開始と終了は `SetWinEventHook`(`EVENT_SYSTEM_MOVESIZESTART` 〜 `EVENT_SYSTEM_MOVESIZEEND`、
  `WINEVENT_OUTOFCONTEXT`)で受け取ります。他のプロセスに DLL を読み込ませず、通知はメッセージループに届きます。
  記憶していないウィンドウは何もせずに返します
- 開始時に、ウィンドウが winwin の置いた大きさのままで、カーソルがサイズ変更の矢印でなければ(PowerToys FancyZones と同じ
  見分け方)、そのウィンドウのスレッドだけに `EVENT_OBJECT_LOCATIONCHANGE` のフックを入れて動くのを待ちます。位置は
  比べません。通知は非同期なので、届いたときにはもう少し動いていることがあるためです。手でサイズを変えた・アプリや Windows が
  大きさを変えた・ハンドルが別のウィンドウに使い回された場合は、大きさが合わないので忘れます
- 開始を待たずに戻さないのは、タイトルバーをクリックしただけでも開始の通知が来るためです。winwin が置いた位置から動いた
  最初の通知でフックを外し、大きさを戻しにかかります。フックが入っているのはドラッグの開始からその時点までだけです
- システムの移動ループは、マウスが動くたびにドラッグ開始時の大きさでウィンドウを置き直します(実機で確かめました。外から
  `SetWindowPos` で大きさを変えても、次の一歩で元に戻ります)。そこで、ループを一度終わらせてから大きさを戻し、新しいループを
  始め直させます(`mover::stop_drag`、`mover::resume_drag`)
  - 最初に動いた時点で、ウィンドウに `WM_CANCELMODE` を送ります(`PostMessage`)。ドラッグ中でないウィンドウには、モードの
    取り消し以上の意味はありません
  - ループが終わった通知(`EVENT_SYSTEM_MOVESIZEEND`)で、ボタンがまだ押されていれば(`GetAsyncKeyState`。左右を入れ替えて
    いれば右ボタン)、元の大きさでカーソルの下に置き、`WM_SYSCOMMAND` の `SC_MOVE | HTCAPTION`(タイトルバーからのドラッグと
    同じ)を送って新しいループを始めさせます。置く位置は、カーソルがつかんでいたタイトルバーの幅の割合と、上端からの距離を
    保ちます。ウィンドウは同期で置くので、新しいループはその矩形から始まります(応答しないウィンドウ(`IsHungAppWindow`)には
    何もしません)
  - 新しいループは Windows 本来のものなので、画面端へのスナップや最大化もそのまま使えます。その開始の通知では大きさを比べず、
    終了の通知で次の仕上げをします
  - ループが止まらなかったとき、止まる前にボタンが離されたときは、次の仕上げで離したときに戻ります
  - 相手のアプリのドラッグに外から割り込むので、次のアプリでは思いどおりにならないことがあります。どれも winwin は止まらず、
    最悪でも離したときに戻るか、何もしないかです
    - システムの移動ループを使わず自前でドラッグするウィンドウ: 開始の通知が来ないので何もしません
    - `WM_CANCELMODE` を `DefWindowProc` に渡さないウィンドウ: ループが止まらず、離したときに戻ります
    - `SC_MOVE` を受け付けないウィンドウ: 元の大きさにはなりますが、ドラッグが途切れます
    - `WM_ENTERSIZEMOVE` / `WM_EXITSIZEMOVE` で描画を止めるなどするアプリ: 1 回のドラッグで 2 回ずつ届きます
    - Chromium 系ブラウザでタブが 1 つのウィンドウのタブをドラッグしたとき: ブラウザ自身が `SC_MOVE` でウィンドウを動かすため、
      タブのドラッグが途中で切れることがあります
- 終了時に仕上げます。Windows が最大化かスナップをした(`IsZoomed`、`IsWindowArranged`)ならそのままにします。戻した大きさで
  カーソルの下にあれば何もしません。そうでなければ、つかんだ位置の幅の割合がカーソルの下に来るよう、戻した大きさで置き直します
- 動いた通知がないまま終了時に winwin が置いた位置(左上)に戻っていれば、クリックだけかドラッグの取り消し(Esc)なので、
  winwin が置いた矩形に戻して記憶も残します
- `IsWindowArranged` は Windows 10 1903 からでインポートライブラリがないため、`GetProcAddress` で引きます(1809 では最大化
  だけを見ます)。DPI の違うモニターに落としたときは、大きさを DPI の比で合わせます。落としたあとに置き直すときは
  `SWP_ASYNCWINDOWPOS` なので、相手が応答しなくても winwin は止まりません
- 記憶は次に配置するときに、なくなったウィンドウ(`IsWindow`)の分を捨てます
- 覚えたことは、そのウィンドウ自身にもウィンドウプロパティ(`SetProp`。`winwin.size`、`winwin.placed`、`winwin.origin`)として残します
  (`marks.rs`)。winwin を起動し直しても、まだ知らないウィンドウのドラッグや配置、リセットではここから読み戻すので、元の大きさ・位置に戻せます。
  値は 64 ビットの数値 3 つに詰めます(`Remembered::pack`。大きさ・DPI は 16 ビット、座標は符号付き 16 ビット、最大化していたかは 1 ビット)。収まらない
  ときと、winwin がウィンドウを忘れたときは消します。リセットに対応する前の版は `winwin.origin` を書かないので、その版が残した値は読み捨てます。ウィンドウが閉じればプロパティも一緒に消えます。Windows はプロパティを
  付けた側がウィンドウの破棄前に外すよう求めていますが、他のアプリのウィンドウではその時を知れません。PowerToys FancyZones も
  同じく元の大きさを他のアプリのウィンドウに残しており、数値だけなので後始末の要るものはありません

### リセット

リセットのショートカットは、前面のウィンドウを winwin が最初に配置する前の外枠の矩形へ戻し、そのとき最大化していれば最大化し直します。
戻す矩形は、ドラッグで戻す大きさと同じく `restore.rs` の `Sizes` が覚えていて(`Remembered::before`)、配置を続けても最初の配置の前のものを
引き継ぎます。戻したあとは、そのウィンドウを忘れてウィンドウプロパティも消します。

- winwin が覚えていないウィンドウ(配置していない、手でサイズを変えた、ドラッグで元の大きさに戻したなど、ドラッグの節で忘れるもの)には何もしません
- 戻す矩形がどのモニターにも映らない(`MonitorFromRect` の `MONITOR_DEFAULTTONULL`。モニターを外したときなど)ときは、位置は今のままにし、
  大きさだけを今のモニターの DPI に合わせて戻します(`Sizes::reset`)
- 最大化中のウィンドウは `SW_RESTORE` してから置きます。DPI の違うモニターへ戻すとウィンドウが自分で大きさを変えることがあるため、置いたあと
  矩形がずれていれば、もう一度だけ置き直します(`mover::reset`)
- テスト用ウィンドウでは開いてから(またはリセットしてから)最初に配置する前の位置・大きさに戻します。ドラッグや手でのサイズ変更では忘れません

### DPI

`winwin.manifest` で Per-Monitor (v2) の DPI 対応と Common Controls v6(メッセージボックス用)を宣言しています。
`build.rs` は `windows-reactor-setup` が作る Windows App Runtime のマニフェスト(WinUI のクラスの登録)に、
リンカの `/MANIFESTINPUT` でこれを足して埋め込みます。座標はすべて物理ピクセルで、ピクセル指定の長さはウィンドウがある
モニターの DPI で拡大します。設定画面の拡大縮小は WinUI に任せています。

### 設定画面

設定画面は WinUI 3 で、`winwin.exe --settings` として別のプロセスで動きます(`settings_ui.rs`)。`windows-reactor` は
最後のウィンドウが閉じるとメッセージループを終え、同じプロセスで WinUI を立ち上げ直すことはできないためです。常駐側
(`settings.rs`)はプロセスを起動し、`RegisterWaitForSingleObject` で終了を待って `WM_APP_SETTINGS_CLOSED` を受け取ります。
WinUI の DLL は設定画面のプロセスでしか読み込まれないので、常駐中のメモリは増えません。

設定画面の幅は変えられず、高さだけ変えられます。幅を広げても右に空白が増えるだけですが、高さを広げると一覧に並ぶ行が増えるためです。最小の大きさは欄とプレビュー全体が収まる大きさで、幅はこの大きさに固定しています(`settings_ui.rs` の `CLIENT`)。

タイトルバーには `Cargo.toml` の `version` を `winwin の設定 - v<version>` の形で出します。

設定画面を開いている間はショートカットをすべて解除し、閉じると(保存したかどうかにかかわらず)設定ファイルを読み直して
登録し直します。開いている間にもう一度開こうとすると、そのプロセスのウィンドウを前面に出します。winwin を終了するとき
(インストーラが閉じるときも)は、開いている設定画面を保存せずに終わらせます。

ショートカットは「変更」で開くダイアログで、押したキーをそのまま記録します。`windows-reactor` 0.100 にはキー入力の
イベントがないため、ダイアログを開いている間だけ低レベルキーボードフック(`keyhook.rs`、`WH_KEYBOARD_LL`)を入れて
キーを受け取ります。フックは winwin のウィンドウが前面にあるときだけキーを取り、Windows や他のアプリには渡しません
(Win でスタートメニューが開いたり、Alt でメニューに移ったりしないように)。どのキーで何が記録されるかは `hotkey.rs` の
`Recorder` が決めます。`windows-reactor` にキー入力のイベントが入ったら、フックをやめてそちらに置き換える予定です。

ショートカットは Windows の設定画面や PowerToys と同じく、アクセントカラーのキーキャップで描きます(`hotkey::keycaps`)。
ボタンではなく、背景をアクセントカラーにした枠です(クリックしても何も起きません)。上に載せる文字の色には、テーマの
基本の背景色(`SolidBackgroundFillColorBase`。ダークでは暗く、ライトでは明るい)を使っています。矢印キーは文字では
なくシェブロンにし、文字と同じ色で描けるよう 2 本の線で描いています。
一覧のキーキャップは、右ペインより一回り小さく描きます(`Caps::SMALL`)。修飾キー 4 つとキー 2 つ(`Win+Ctrl+Alt+Shift+Left, Up`)
でも、配置の列と並べて収まる大きさです。

左下の「テーマ」で、設定画面とトレイメニューをライト・ダークに固定できます(既定は Windows の設定に合わせる)。設定画面
には選んだ時点で反映し、保存すると設定ファイルの `theme` に書きます。

ウィンドウの閉じるボタンも、未保存の変更があれば確認を出します。`windows-reactor` はウィンドウの HWND を渡さないので、
スレッドのウィンドウからクラス名 `WinUIDesktopWin32WindowClass` のものを探してサブクラス化し、`WM_CLOSE` をコンポーネントへの
メッセージ(キャンセルと同じ)に置き換えています。見つからなければ、閉じるボタンは確認なしで閉じます。

この確認ダイアログの「閉じる」は、変更を捨てる操作なので警告色(WinUI のライトテーマの `SystemFillColorCritical`、
`#C42B1C`)に白文字で塗ります。ダークテーマの同じ色(`#FF99A4`)は淡く警告に見えないため、テーマにかかわらずこの色です。
`windows-reactor` の `ContentDialog` は自前のボタンの見た目を変えられないため、ダイアログ自身のボタンは持たせず、同じ並びの
ボタン 2 つを内容に置き、「閉じる」だけ `resource_overrides` でボタンの色のリソースを置き換えています。Esc はダイアログ
自身が「戻る」と同じく閉じます。

### テスト用ウィンドウ

設定画面の一覧の下のボタンで、保存前のショートカットを試すためのウィンドウを開きます(`testwin.rs`)。設定画面と同じ
プロセス・同じスレッドに Win32 のウィンドウを作り、`windows-reactor` のメッセージループにそのまま乗せています。常駐側は
設定画面を開いている間ショートカットを解除しているので、その間はテスト用ウィンドウが `RegisterHotKey` で登録します。
押されると、前面のウィンドウではなく必ずテスト用ウィンドウを `mover::place` で動かし、フォーカスを奪わずに最前面へ
出します。切り替えショートカットの進め方と修飾キーの監視は常駐側と同じです(`cycle.rs` と `modifiers_held`)。

登録するのは `Editor::trial_config` が返す、その時点で保存できる行だけです。入力途中の行は飛ばします。設定画面の
`update` のたびに渡し直し、組み合わせが変わったときだけ登録し直します(切り替えの途中で最初に戻らないように)。
ショートカットを記録するダイアログを開いている間は、すべて解除します。

見た目は `WS_POPUP | WS_THICKFRAME` のウィンドウで、`WM_NCCALCSIZE` で枠をすべてクライアント領域にし、
`DWMWA_SYSTEMBACKDROP_TYPE`(`DWMSBT_TRANSIENTWINDOW`、アクリル)と `DwmExtendFrameIntoClientArea` で全面を
すりガラスにしています。Windows 11 22H2 より前はこの属性がないので、半透明(`WS_EX_LAYERED`)の単色で描きます。
すりガラスはテーマにかかわらず明るい色です(ダークのすりガラスはくすんだ灰色に見えるため)。

- DWM はアクティブでないウィンドウのすりガラスを灰色の単色に替えるので、`WM_NCACTIVATE` には常にアクティブとして
  `DefWindowProc` を呼びます。lParam を -1 にして、そのとき従来の枠がクライアント領域の上に描かれるのを防ぎます
  (`WM_NCPAINT` も何もしません)。フォーカスを奪わずに表示すると一度も `WM_NCACTIVATE` が届かないので、表示した直後に
  自分で送ります
- Windows 11 が描く 1px の枠は `DWMWA_BORDER_COLOR` で消しています
- アイコンは設定画面と同じく `icon.rs` で描き、`WM_SETICON` で付けます(Alt+Tab とタスクバーに出るため)
- タイトルバーもボタンもなく、どこでもドラッグでき、端でサイズを変えられます。`WM_GETMINMAXINFO` で最小サイズを 1px に
  しているので、配置どおりの大きさになります
- 普通のウィンドウなのでタスクバーと Alt+Tab に出ます。`WS_EX_TOOLWINDOW` にするとすべての仮想デスクトップに表示される
  ためです。常駐側が設定画面を前面に出すとき(`settings.rs` の `bring_forward`)は、クラス名でこのウィンドウを除きます
- 開いている間は設定画面を最前面(`HWND_TOPMOST`)にします。テスト用ウィンドウが画面いっぱいになっても閉じられるように
  するためです
- Alt+F4 で閉じようとすると、設定画面に伝えて閉じます。設定画面を閉じるとプロセスごと消えます

一覧の行はドラッグで並べ替えられます(`ListView` の `CanReorderItems`)。並べ替えは WinUI が先に行うので、各行の
`Tag` に行の ID を入れておき、`on_reordered` で受け取った ID の順を `Editor::reorder` に渡します。ID は行と一緒に動くので、
`windows-reactor` が次の描画で合わせる並びは、WinUI が並べた並びと一致します。

「上へ」「下へ」は逆に、ID をその場に残して 2 行の中身だけを入れ替えます(`Editor::move_selected`)。ID ごと動かすと
`windows-reactor` が `ListViewItem` を一度コレクションから外して入れ直し(`ListView` の削除と追加のアニメーションが
走ります)。中身の入れ替えなら、2 行の表示を書き換えるだけです。
ドラッグのあとも `windows-reactor` は落とした行を同じ位置へ入れ直しますが、動かす行は 1 つだけです。

一覧の選択は `Editor` が行の ID の集合として持ち、選ばれた行は各行の中身として自前で描きます(灰色の背景と、左端の
アクセント色の縦線)。`windows-reactor` の `ListView` は選択を `SelectedIndex` 1 つでしか受け渡しできず、WinUI の
`Extended` モードで選んだ複数の行を受け取れないためです。`ListView` 自体は `Single` モードのまま、描画のたびに
`selected_index(None)` を渡します。クリックや矢印キーで WinUI が行を選ぶと、その番号と、そのとき押されている
Shift・Ctrl(`GetAsyncKeyState`)を `Editor::click` に渡し、次の描画で WinUI の選択は外れます(`windows-reactor` は
イベントで受け取った値を覚えているので、渡す値が `None` のままでも外し直します)。選択が残らないので、同じ行を
続けてクリックしても毎回イベントが届き、Shift+クリックで広げた範囲を普通のクリックで 1 行に戻せます。

- 普通のクリックはその行だけを選び、範囲の起点にします。Ctrl+クリックは行を選択に足すか外し、起点にします。
  Shift+クリック(Shift+↑↓)は起点からその行までを選び直し、Ctrl も押していれば今の選択に足します
- 右ペインで編集できるのは、選ばれている行が 1 つのときだけです(`Editor::current`)。2 つ以上なら右ペインと
  「上へ」「下へ」は使えず、「複製」「削除」は選ばれている行すべてに対して行います
- 「複製」は選ばれている行の写しを、並び順のまま最後の選択行の下にまとめて入れ、写しを選びます

WinUI の選択を使わないので、行を追加した描画で `SelectedIndex` に今ある行を超える番号が渡ること(WinUI が拒み、
`windows-reactor` はそれを致命的なエラーとしてプロセスを止めます)もありません。

右側のプレビューは、設定画面を開いたモニターの作業領域を `layout.rs` の `miniature` で縮め、
そこへ配置を当てはめて描きます(`Draft::picture`)。ウィンドウは薄い塗りと枠線の角丸の矩形です。
「維持」にした幅・高さは元にするウィンドウがないので画面の半分として描き、その軸の辺のうち画面端に接していない
辺(位置がウィンドウの大きさ次第で変わる辺)を破線にします(`draft::Frame`)。WinUI の `Border` は破線を描けないので、
破線にする辺は枠線の太さを 0 にし、角の丸みを除いたまっすぐな部分に短い `Line` を並べて重ねます(`draft::dashes`)。

幅の欄が一時的に `5` になるのは入力途中では普通のことなので、入力そのものは拒まずに `Draft` へ文字列のまま入れておき、
保存時に `Editor::build_config` がまとめて検証します。ただし保存を押すまで何も出ないと範囲外の値が受け付けられたように
見えるので、幅・高さが比率として読めないあいだは欄の下にその理由を赤字で出します(`Draft::size_problem`)。
WinUI のコントロールは、値を設定し直しただけでも変更イベントを出すので、`Editor::edit` は値が変わったときだけ
「変更あり」にします。

### 状態の持ち方

常駐側のウィンドウプロシージャから触る状態は `thread_local!` の `RefCell` に置いています(`app.rs` の `with_app`)。このクロージャの中では、自分のウィンドウにメッセージを送る API(メッセージボックス、
コントロールへのテキスト設定など)を呼ばないでください。ウィンドウプロシージャが再入して同じ `RefCell` を借りようとし、
借用に失敗します(`try_borrow_mut` なので落ちはしませんが、その処理は黙って捨てられます)。値を取り出してから
クロージャの外で呼ぶのが決まりです。

### Windows インストーラ(NSIS)

`installer/installer.nsi` は winwin 用に書いた NSIS スクリプトです。winwin は Tauri を使っていないので Tauri の
テンプレートは使えませんが、振る舞いは draftpad のインストーラ(`draftpad/src-tauri/installer.nsi`)に揃えています。

| 項目 | 内容 |
|---|---|
| インストール先 | ユーザー単位(`%LOCALAPPDATA%\winwin`)。管理者権限を求めません。前回のインストール先があればそちらを既定にします |
| 旧バージョンがあるとき | 確認せずに上書きします(draftpad が既定で選ぶ「上書きする」と同じ) |
| 起動中の winwin | 確認ダイアログを出さずに終了させます。インストーラ・アンインストーラのどちらも |
| 同梱するもの | `winwin.exe` と Windows App Runtime のファイル一式(`payload.ps1` が `target/release` から一覧を作る)。`windows-reactor-setup` が一緒に置く WebView2 用の `Microsoft.Web.WebView2.Core.dll` は使わないので入れません。WinUI の言語ごとのリソースのフォルダ(`de-DE` など 90 余り)も、`ja-JP` と既定の `en-US` だけを入れます。`payload.ps1` は各ファイルの大きさを CI のログに出します |
| インストール後 | ログの画面で止まらず、完了画面まで自動で進みます |
| 完了画面 | 「winwin を起動する」「デスクトップにショートカットを作成する」「設定画面を開く」。ショートカットは上書きインストールのときだけ外した状態で出します。「設定画面を開く」は draftpad にない項目で、「winwin を起動する」を外すと選べなくなります |
| スタートメニュー | `winwin` のショートカットを置きます |
| アンインストール | 「設定」→「アプリ」に登録します。インストールしたファイル(一覧にあるものだけ)・ショートカットに加えて、自動起動の `Run` の値も消します。`%APPDATA%\winwin` の設定は、消すかどうかを聞きます(既定は残す。サイレント実行では残します) |

起動中の winwin は、隠しウィンドウのクラス名 `winwin.main` を `FindWindow` で探し、`WM_CLOSE` を送って終わらせます。
トレイメニューの「終了」と同じ後始末(通知領域アイコンの削除など)を通るためです。`src/win/app.rs` のクラス名を
変えるときは、スクリプトの `MAIN_CLASS` も合わせてください。

完了画面の「設定画面を開く」は、MUI2 の完了画面にチェックボックスが 2 つしかないため、`FinishPageShow` で 3 つ目として
足しています。位置は MUI2 の配置(1 つ目が 90u、以降 20u おき)に合わせた 130u です。設定画面は、起動した winwin の隠し
ウィンドウが現れるのを待ってから `winwin.exe` をもう一度起動して開かせます。起動中にもう一度起動すると設定画面が開く
振る舞いを使っているので、`src/win/app.rs` のこの動きを変えるときはスクリプトも直してください。

スクリプトは BOM 付きの UTF-8 です。BOM がないと、Windows の `makensis` はシステムの文字コード(英語版の
ランナーでは CP1252)で読むため、スクリプトに直接書いた日本語(完了画面のチェックボックスやメッセージ)が
文字化けします。CI はさらに `/INPUTCHARSET UTF8` を渡しています。

スタブは NSIS 既定の 32 ビット(x86)版です。64 ビットでない Windows では `.onInit` で止めます。
Wine で試すときに 32 ビットの Wine がなければ、`makensis "-XTarget amd64-unicode" ...` で 64 ビット版を作れば動きます
(Linux の NSIS パッケージには amd64 のスタブが入っています)。

### 通知領域アイコン

アイコンの絵は `art.rs` の 1 か所にあり、ピクセルで描きます。アイコンファイルは持ちません。

- 通知領域: 実行時に `win/icon.rs` が求められた大きさで描きます
- 設定画面のタイトルバー: 同じく実行時に描き、`WM_SETICON` で付けます(`settings_ui.rs` の `adopt_window`。閉じるボタンの
  サブクラス化と同じ場所で、ウィンドウが見つからなければ既定のアイコンのままです)
- exe 自体(エクスプローラー、タスクバー、Alt+Tab): `build.rs` が 16〜256px の 8 サイズを描き、`icon_res.rs` でリソース
  ファイル(.res)にしてリンカに渡します。`rc.exe` もアイコンファイルも要りません。WinUI のウィンドウのタスクバーの
  アイコンは `WM_SETICON` ではなく exe のアイコンが使われるため、こちらが要ります

右クリックメニューは Win32 の標準メニューです。Windows のダークモード(または設定の `theme`)に合わせるため、表示のたびに
uxtheme.dll の非公開の関数(序数 135 `SetPreferredAppMode`、136 `FlushMenuThemes`)を呼んでいます(`app.rs` の
`apply_menu_theme`)。
Windows の更新でなくなった場合は、明るい色のメニューに戻るだけです。

## バージョニングとリリース

[セマンティック バージョニング](https://semver.org/lang/ja/)に従います。0.x の間は、ユーザーに見える機能の追加や
挙動の変更で minor を、修正だけなら patch を上げます。

バージョンの実体は `Cargo.toml` の `version` です。書き換えたら `cargo update -p winwin` で `Cargo.lock` も追随させてください。

`main` ブランチで `Cargo.toml` の `version` が上がると、GitHub Actions が `winwin-v<version>` タグの Release を作り、
インストーラ `winwin_<version>_x64-setup.exe` と macOS 版の `winwin_<version>_macos-arm64.dmg` を添付します。インストーラは常に同じフォルダの `winwin.exe` を
上書きするので、自動起動のレジストリが指す exe のパスは更新後も変わりません。

Pull Request でビルドしたものも、バージョンは Release と同じ `0.12.0` の形です。コミットのハッシュは付けません。
eleven-zip のインストーラが、ファイル名にハッシュを付けたときだけ Microsoft Defender に `Trojan:Win32/Bearfoos.A!ml`
として検出されたためです(#188)。どのコミットのビルドかは、Pull Request に CI が書くコメントで確かめます。

### 上げ忘れを CI が止めます

上げ忘れても Release ジョブは黙ってスキップするだけなので、`winwin-version.yml` が Pull Request を赤くします。
`winwin/` を変更する Pull Request では、次のどれかに当たると落ちます。

- バージョンが base ブランチの先端と同じ、または古い
- `Cargo.toml` と `Cargo.lock` のバージョンが食い違っている

リリースするつもりがない変更(ドキュメントだけ、CI だけ、など)では、Pull Request に `no-release` ラベルを付けてください。

依存ライブラリの新しいバージョンは Dependabot が週に 1 回確かめ、見つかると Pull Request を作ります(設定は `.github/dependabot.yml`)。この Pull Request には `no-release` ラベルが付き、ビルドとテストがすべて通ると `.github/workflows/dependabot-merge.yml` がマージします。バージョンは上げず、更新は次のリリースに含めて出します。手で確かめる項目は次にこのアプリを変更する Pull Request でまとめて確認し、その Pull Request の本文に、取り込んだ更新を書きます。

配布物はコード署名をしていないため、ダウンロードしたインストーラの実行時に SmartScreen の警告が出ます。
手順は README.md に書いてあります。
